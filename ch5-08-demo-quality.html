Demo - Advanced Data Quality Checks and Expectations em Spark Declarative Pipelines

Visão Geral

Esta demonstração mostra gerenciamento de qualidade de dados de nível corporativo usando Spark Declarative Pipelines (Lakeflow), com expectations avançadas de qualidade e padrões de quarentena. Você construirá uma arquitetura medallion abrangente que implementa três padrões críticos de engenharia de dados: validação baseada em intervalos (range), evolução automática de schema e processamento de quarentena sem perda de dados.

A demo simula um cenário do mundo real onde dados de pedidos chegam com níveis variados de qualidade e schemas em evolução. Usando padrões oficiais da Databricks, você processará esses dados através das camadas bronze, silver e gold, implementando controles robustos de qualidade que capturam anomalias nos dados, lidam com mudanças de schema de forma transparente e garantem zero perda de dados através de mecanismos inteligentes de quarentena.

Esta demonstração usa uma abordagem de duas execuções: a Execução 1 estabelece uma baseline limpa com 157 registros perfeitos para validar o framework de qualidade, enquanto a Execução 2 introduz 60 registros contendo problemas de qualidade intencionais e evolução de schema, para demonstrar a resiliência e as capacidades de monitoramento do sistema.

Objetivos de Aprendizado

Ao final desta demonstração, você será capaz de:

  • Implementar validação de dados abrangente usando 6 expectations de qualidade cobrindo checagens de NOT NULL, intervalos numéricos e validações de data com sintaxe de constraint apropriada
  • Lidar com evolução automática de schema sem alterações no código do pipeline, usando design flexível da camada bronze e schema hints
  • Construir padrões de quarentena usando a lógica inversa oficial da Databricks para capturar registros inválidos, mantendo zero perda de dados e rastreamento detalhado de falhas
  • Monitorar métricas de qualidade de dados e analisar a performance das expectations para identificar problemas específicos de qualidade e desenvolver estratégias de remediação

D. Crie a Camada Bronze - Ingestão Bruta com Evolução de Schema

A camada bronze implementa evolução de schema usando a função read_files com tratamento flexível de colunas e schema hints para compatibilidade com colunas futuras.

D1. Crie a Tabela Bronze com Suporte a Evolução de Schema

Copie o código abaixo no seu arquivo bronze_ingestion.sql. Esta implementação usa uma abordagem baseada em STRING para máxima flexibilidade de schema e inclui schema hints para colunas futuras.



------------------------------------------
-- CAMADA BRONZE: INGESTÃO DE DADOS BRUTOS
------------------------------------------
CREATE OR REFRESH STREAMING TABLE dq_1_bronze.sales_bronze_raw_demo
AS
SELECT 
  -- Campos de negócio principais (todos como STRING para flexibilidade de schema)
  CAST(subsidiary_id AS STRING) AS subsidiary_id,
  CAST(order_id AS STRING) AS order_id,
  CAST(order_timestamp AS STRING) AS order_timestamp,
  CAST(customer_id AS STRING) AS customer_id,
  CAST(region AS STRING) AS region,
  CAST(country AS STRING) AS country,
  CAST(city AS STRING) AS city,
  CAST(channel AS STRING) AS channel,
  CAST(sku AS STRING) AS sku,
  CAST(category AS STRING) AS category,
  CAST(qty AS STRING) AS qty,
  CAST(unit_price AS STRING) AS unit_price,
  CAST(discount_pct AS STRING) AS discount_pct,
  CAST(coupon_code AS STRING) AS coupon_code,
  CAST(total_amount AS STRING) AS total_amount,
  CAST(order_date AS STRING) AS order_date,

  -- Novas colunas para evolução de schema (serão nulas inicialmente)
  CAST(order_status AS STRING) AS order_status,
  CAST(shipping_cost AS STRING) AS shipping_cost,

  -- Coluna de dados resgatados (rescued) para problemas de parsing
  CAST(_rescued_data AS STRING) AS _rescued_data,

  -- Colunas de metadata para rastreamento de lineage
  _metadata.file_name AS source_file,
  _metadata.file_modification_time AS file_mod_time
FROM STREAM read_files(
  '${source}',
  format => 'csv',
  schemaHints => 'order_status STRING, shipping_cost STRING'
);

Revise os Padrões de Design da Camada Bronze:

Estratégia de Evolução de Schema: - Armazenamento como STRING: todas as colunas de negócio armazenadas como STRING para máxima flexibilidade e compatibilidade - Schema pré-definido: inclui tanto as colunas originais quanto duas colunas futuras, para evolução transparente - Schema hints: declara as novas colunas esperadas (order_status, shipping_cost) mesmo quando ainda não presentes nos dados - Tratamento de nulos: novas colunas serão NULL para arquivos existentes, e preenchidas para arquivos futuros

Data Lineage e Proteção: - Auto Loader: a função read_files permite processamento incremental com gerenciamento de checkpoint - Captura de metadata: nomes de arquivo de origem e timestamps de modificação para data lineage completo - Dados resgatados (rescued): a coluna _rescued_data captura quaisquer problemas de parsing para investigação e recuperação - Referência de parâmetro: ${source} permite configuração dinâmica de caminho

Benefícios Técnicos: - Nenhuma alteração no código do pipeline é necessária quando novas colunas chegam - Compatibilidade retroativa com arquivos de dados existentes - Compatibilidade futura com requisitos de negócio em evolução

Para mais informações sobre a funcionalidade de schema hints, veja a documentação da Databricks sobre schema hints.

D2. Crie a Tabela Bronze Clean

Crie uma tabela Bronze intermediária de streaming que realiza conversão de tipo segura a partir dos dados brutos ingeridos, sem aplicar nenhuma checagem de qualidade. Esta etapa garante uma conversão de tipo limpa antes da validação de dados.

  • Cria uma tabela Bronze de streaming limpa a partir do stream de dados de origem.
  • Usa TRY_CAST para converter tipos de dados (datas, números) com segurança, sem falhar em dados ruins.
  • Repassa todas as colunas sem ainda aplicar nenhum filtro de qualidade de dados.


--========================================================================
-- CAMADA BRONZE: TABELA DE TRANSFORMAÇÃO INTERMEDIÁRIA
-- Propósito: conversão de tipo limpa a partir do Bronze Raw (ainda sem checagens de qualidade)
--========================================================================

CREATE OR REFRESH STREAMING TABLE dq_1_bronze.sales_bronze_clean_demo
COMMENT "Tabela intermediária - apenas conversão de tipo, sem checagens de qualidade"
AS
SELECT
  -- Repasse direto e conversão de tipo segura
  subsidiary_id,
  order_id,
  TRY_CAST(order_timestamp AS TIMESTAMP) AS order_timestamp,
  TRY_CAST(order_date AS DATE) AS order_date,
  customer_id,
  region,
  country,
  city,
  channel,
  sku,
  category,
  TRY_CAST(qty AS INT) AS qty,
  TRY_CAST(unit_price AS DOUBLE) AS unit_price,
  TRY_CAST(discount_pct AS DOUBLE) AS discount_pct,
  TRY_CAST(total_amount AS DOUBLE) AS total_amount,
  coupon_code,
  order_status,
  TRY_CAST(shipping_cost AS DOUBLE) AS shipping_cost,
  source_file

FROM STREAM dq_1_bronze.sales_bronze_raw_demo;

E. Crie a Camada Silver com Data Quality Expectations e Lógica de Quarentena

  • Nesta camada, primeiro converteremos os tipos das colunas para seus formatos de dados apropriados.
  • Em seguida, aplicaremos as expectations de qualidade de dados.
  • Por fim, com base nessas expectations, separaremos os dados em duas tabelas: uma para registros limpos e outra para registros inválidos, usando lógica inversa.

E1. Entendendo o Framework de Data Quality Expectations

Antes de criar tabelas com expectations, entenda o framework de expectations e por que cada validação é crítica para a qualidade de dados corporativa.

Sintaxe de Expectation:

CONSTRAINT <constraint_name> 
  EXPECT (<condition>) 
  ON VIOLATION <action>

Ações de Violação Disponíveis: - WARN (padrão): registros inválidos são incluídos, mas a violação é registrada para monitoramento - DROP ROW: registros inválidos são excluídos da tabela target - FAIL UPDATE: o pipeline para e requer intervenção manual

Nossa Estratégia: Usamos WARN (padrão) para todas as expectations, garantindo que o pipeline continue em execução e que todos os registros sejam mantidos para análise de quarentena.

Nossas 6 Expectations de Qualidade Abrangentes:

Categoria 1: Validação de Chaves de Negócio (Crítica para Integridade de Dados) 1. check_subsidiary_id: todo pedido deve ter um identificador de subsidiária para atribuição correta 2. check_customer_id: deve identificar qual cliente fez o pedido, para analytics e compliance 3. check_sku: deve identificar qual produto foi pedido, para rastreamento de inventário e receita

Categoria 2: Validações Baseadas em Intervalo (Aplicação de Regras de Negócio)

  1. valid_discount_range: o desconto deve estar entre 0% e 100% (captura descontos negativos e valores impossíveis)
  2. valid_date_range: datas de pedido dentro dos últimos 4 anos (captura dados arquivados e datas futuras)

NOTA: Como nossos dados são estáticos, estamos checando a constraint valid_date_range em relação a 01-01-2026.

Categoria 3: Validação de Evolução de Schema (Qualidade de Novas Colunas)

  1. valid_shipping_cost: o custo de frete deve estar entre $0 e $100 (valida a nova coluna de negócio)

Nota sobre Evolução de Schema: A expectation valid_shipping_cost se aplica a uma coluna não presente nos dados iniciais, mas esperada em arquivos futuros. Assim que a coluna aparece, a expectation aplica automaticamente a validação. Para detalhes, veja Schema Evolution Pattern.

E2. Entendendo o Padrão de Quarantine Records

Quarantine records em Spark Declarative Pipelines são registros que violam expectations de qualidade de dados e são encaminhados a uma tabela de quarentena separada, para análise e remediação. Esse padrão corporativo garante:

Benefícios: - Zero perda de dados: dados inválidos são isolados para revisão, sem serem descartados ou causarem falhas no pipeline - Rastreamento detalhado: metadados capturam quais expectations específicas falharam para cada registro - Workflows flexíveis: permite processos de remediação, reprocessamento e melhoria de qualidade - Compliance de auditoria: registro completo de problemas de qualidade de dados para requisitos regulatórios

Padrão de Implementação: - Tabela principal: contém expectations com ação WARN (registra violações, mantém os registros) - Lógica de quarentena: usa lógica inversa (condição NOT) para identificar registros que falharam - Processamento paralelo: registros válidos e inválidos fluem simultaneamente para tabelas separadas

Saiba Mais:
💡 Para informações abrangentes sobre frameworks de quarentena e boas práticas, veja a documentação da Databricks sobre padrões de expectations e quarentena de registros inválidos.

Adicione o código a seguir ao seu arquivo silver_transformations.sql. Isso cria a tabela principal de quarentena com as 6 expectations de qualidade de dados definidas.


--========================================================================
-- CAMADA SILVER - PASSO 1: TABELA DE QUARENTENA COM EXPECTATIONS
-- Propósito: definir a estrutura da tabela e as 6 expectations de qualidade de dados
--========================================================================

CREATE OR REFRESH STREAMING TABLE dq_2_silver.sales_silver_dq_demo
(
  -- Colunas de negócio com os tipos de dados apropriados
  subsidiary_id STRING,
  order_id STRING,
  order_timestamp TIMESTAMP,
  order_date DATE,
  customer_id STRING,
  region STRING,
  country STRING,
  city STRING,
  channel STRING,
  sku STRING,
  category STRING,
  qty INT,
  unit_price DOUBLE,
  discount_pct DOUBLE,
  total_amount DOUBLE,
  coupon_code STRING,
  order_status STRING,
  shipping_cost DOUBLE,
  source_file STRING,

  -- Colunas de rastreamento de qualidade para análise de quarentena
  is_quarantined BOOLEAN,
  quarantine_reason STRING,

  --========================================================================
  -- 6 EXPECTATIONS DE QUALIDADE DE DADOS (AÇÃO WARN PARA O PADRÃO DE QUARENTENA)
  --========================================================================

  CONSTRAINT check_subsidiary_id 
    EXPECT (subsidiary_id IS NOT NULL),

  CONSTRAINT check_customer_id 
    EXPECT (customer_id IS NOT NULL),

  CONSTRAINT check_sku 
    EXPECT (sku IS NOT NULL),

  CONSTRAINT valid_discount_range
    EXPECT (discount_pct IS NULL OR (discount_pct >= 0 AND discount_pct <= 100)),

  -- Como os dados são estáticos, verificamos que order_date está entre 01-01-2026 e 4 anos antes, em vez de usar a data atual.
  CONSTRAINT valid_date_range 
    EXPECT (order_date IS NULL OR 
        (order_date >= DATE_SUB(DATE '2026-01-01', 1460) AND 
          order_date <= DATE '2026-01-01')),

  CONSTRAINT valid_shipping_cost EXPECT (
    CASE WHEN shipping_cost IS NOT NULL THEN shipping_cost > 0 AND shipping_cost < 100 ELSE TRUE END
  )
)
COMMENT "Tabela de quarentena com 6 expectations - suporta o padrão de lógica inversa"
TBLPROPERTIES (
  'quality.layer' = 'silver_quarantine',
  'quality.pattern' = 'inverse_logic'
)
PARTITIONED BY (is_quarantined);

Revise o Framework de Expectations:

Resumo das Expectations:

# Nome da Expectation Valida Intervalo/Regra Exemplo de Violação
1 check_subsidiary_id Chave de Negócio NOT NULL subsidiary_id ausente
2 check_customer_id Chave de Negócio NOT NULL customer_id ausente
3 check_sku Chave de Negócio NOT NULL sku ausente
4 valid_discount_range Desconto 0%-100% discount = -10,73% ou 120%
5 valid_date_range Data Últimos 4 anos date = 1930-12-31
6 valid_shipping_cost Frete $0-$100 shipping_cost = -5 ou 150

Design de Rastreamento de Qualidade: - is_quarantined: flag booleano indicando se o registro falhou em alguma expectation - quarantine_reason: string detalhada listando todas as validações que falharam, para remediação - Particionamento: separa dados em quarentena e dados válidos para otimização de performance

Propriedades da Tabela: - Tags de metadata identificam esta como uma implementação do padrão de quarentena - Permite que ferramentas de monitoramento e governança reconheçam o framework de qualidade

E5. Crie o Flow de Lógica Inversa para Popular a Quarentena

Adicione o flow de lógica inversa para popular a tabela de quarentena com informações de rastreamento de qualidade. Este flow implementa o padrão de quarentena oficial da Databricks, usando lógica inversa para identificar e sinalizar registros que falham em qualquer expectation de qualidade.


--========================================================================
-- CAMADA SILVER - PASSO 2: FLOW PARA APLICAR A LÓGICA INVERSA
-- Propósito: calcular a flag is_quarantined e popular a tabela de quarentena
--========================================================================

CREATE FLOW apply_inverse_logic_flow
AS
INSERT INTO dq_2_silver.sales_silver_dq_demo BY NAME
SELECT
  -- Repassa todas as colunas de negócio
  subsidiary_id,
  order_id,
  order_timestamp,
  order_date,
  customer_id,
  region,
  country,
  city,
  channel,
  sku,
  category,
  qty,
  unit_price,
  discount_pct,
  total_amount,
  coupon_code,
  order_status,
  shipping_cost,
  source_file,

  --========================================================================
  -- LÓGICA INVERSA: marca como quarentena se QUALQUER expectation falhar
  --========================================================================
  NOT (
    (subsidiary_id IS NOT NULL) AND
    (customer_id IS NOT NULL) AND
    (sku IS NOT NULL) AND
    (discount_pct IS NULL OR (discount_pct >= 0 AND discount_pct <= 100)) AND
    (order_date IS NULL OR 
     (order_date >= DATE_SUB(DATE '2026-01-01', 1460) AND 
      order_date <= DATE '2026-01-01')) AND
    (shipping_cost IS NULL OR (shipping_cost > 0 AND shipping_cost < 100))
  ) AS is_quarantined,

  --========================================================================
  -- CONSTRÓI A STRING DETALHADA DO MOTIVO DA QUARENTENA
  --========================================================================
  CONCAT_WS('; ',
    CASE WHEN subsidiary_id IS NULL 
         THEN 'subsidiary_id ausente' END,
    CASE WHEN customer_id IS NULL 
         THEN 'customer_id ausente' END,
    CASE WHEN sku IS NULL 
         THEN 'sku ausente' END,
    CASE WHEN discount_pct IS NOT NULL AND (discount_pct < 0 OR discount_pct > 100) 
         THEN 'discount_pct inválido (deve ser 0-100)' END,
    CASE WHEN order_date IS NOT NULL AND 
              (order_date < DATE_SUB(DATE '2026-01-01', 1460) OR order_date > DATE '2026-01-01') 
         THEN 'order_date inválido (fora do intervalo de 4 anos)' END,
    CASE WHEN shipping_cost IS NOT NULL AND (shipping_cost <= 0 OR shipping_cost >= 100)
         THEN 'shipping_cost inválido (deve ser 0-100)' END
  ) AS quarantine_reason

FROM STREAM dq_1_bronze.sales_bronze_clean_demo;

Revise a Implementação da Lógica Inversa:

Lógica da Flag de Quarentena: - Um wrapper NOT() envolve todas as expectations combinadas com lógica AND - Se QUALQUER expectation falhar, o registro é marcado como is_quarantined = TRUE - Se TODAS as expectations passarem, o registro é marcado como is_quarantined = FALSE

Rastreamento Detalhado de Falhas: - CONCAT_WS() constrói motivos de falha separados por ponto e vírgula - Cada instrução CASE checa um tipo específico de violação - Fornece informação acionável para times de remediação de dados - String vazia para registros que passam em todas as validações

Benefícios do Streaming Flow: - Processa registros continuamente à medida que chegam - Mantém baixa latência para monitoramento de qualidade em tempo real - Permite identificação imediata de quarentena para workflows operacionais

E6. Crie Tabelas Separadas para Registros Válidos e em Quarentena

Crie tabelas separadas para registros válidos e em quarentena, permitindo workflows de zero perda de dados e processamento paralelo. Adicione este código ao seu arquivo silver_transformations.sql.


--========================================================================
-- CAMADA SILVER - PASSO 3: SEPARAR OS CAMINHOS DE DADOS VÁLIDOS E INVÁLIDOS
--========================================================================

--========================================================================
-- CAMINHO DE REGISTROS VÁLIDOS - Dados limpos para analytics
--========================================================================

CREATE OR REFRESH STREAMING TABLE dq_2_silver.sales_silver_valid_demo
COMMENT "Registros limpos que passam nas 6 checagens de qualidade - prontos para analytics"
AS
SELECT * EXCEPT (is_quarantined, quarantine_reason)
FROM STREAM dq_2_silver.sales_silver_dq_demo
WHERE is_quarantined = FALSE;

--========================================================================
-- CAMINHO DE REGISTROS EM QUARENTENA - Dados inválidos para remediação
--========================================================================

CREATE OR REFRESH STREAMING TABLE dq_2_silver.sales_silver_quarantined_demo
COMMENT "Registros inválidos com violações de qualidade - requer remediação"
AS
SELECT *
FROM STREAM dq_2_silver.sales_silver_dq_demo
WHERE is_quarantined = TRUE;

Revise a Implementação Oficial do Padrão de Quarentena:

Arquitetura de Zero Perda de Dados: - Tabela de origem: contém expectations com ação WARN (registra violações, mantém todos os registros) - Caminho válido: registros onde is_quarantined = FALSE (passaram em todas as checagens de qualidade) - Caminho de quarentena: registros onde is_quarantined = TRUE (falharam em uma ou mais checagens) - Garantia matemática: Total de Registros = Registros Válidos + Registros em Quarentena

Benefícios do Processamento Paralelo: - Workflow de analytics: consome apenas dados validados e limpos de sales_silver_valid_demo - Workflow de remediação: processa dados em quarentena com informações detalhadas de falha - Workflow de monitoramento: rastreia métricas de qualidade em ambos os streams - Otimização de performance: tabelas separadas permitem escalonamento e otimização independentes

--========================================================================
-- CAMADA GOLD: MATERIALIZED VIEW PARA ANALYTICS DE NEGÓCIO
--========================================================================

CREATE OR REFRESH MATERIALIZED VIEW dq_3_gold.sales_analytics_demo
COMMENT "Métricas de negócio agregadas a partir de dados de vendas validados"
AS
SELECT
  region,
  country,
  category,
  COUNT(DISTINCT order_id) AS total_orders,
  COUNT(DISTINCT customer_id) AS unique_customers,
  SUM(qty) AS total_quantity_sold,
  ROUND(SUM(total_amount), 2) AS total_revenue,
  ROUND(AVG(total_amount), 2) AS avg_order_value,
  ROUND(AVG(discount_pct), 2) AS avg_discount_pct,
  MIN(order_date) AS earliest_order_date,
  MAX(order_date) AS latest_order_date,
  CURRENT_TIMESTAMP() AS last_refreshed_at
FROM dq_2_silver.sales_silver_valid_demo
GROUP BY region, country, category;
