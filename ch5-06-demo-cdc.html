Demo - Automatizando SCD Type 2 com AUTO CDC em Apache Spark Declarative Pipelines

Visão Geral

Esta demonstração mostra como implementar Change Data Capture (CDC) automatizado para padrões Slowly Changing Dimension (SCD) Type 2 usando Apache Spark™ Declarative Pipelines.

Você aprenderá a construir um pipeline de streaming ponta a ponta que processa automaticamente mudanças em dados de clientes (inserções, atualizações e exclusões), mantendo registros históricos completos. A demo usa dados reais de clientes de varejo do Databricks Marketplace e demonstra como o AUTO CDC INTO simplifica operações complexas de CDC que tradicionalmente exigiam codificação manual.

Você criará uma arquitetura em múltiplas camadas (Bronze → Silver → Gold) com checagens automatizadas de qualidade de dados, processamento incremental e materialized views para analytics de clientes tanto atuais quanto históricos.

Objetivos de Aprendizado

Ao final deste notebook, você será capaz de:

  • Configurar e implementar AUTO CDC INTO para processamento automatizado de Change Data Capture em Apache Spark™ Declarative Pipelines com padrões SCD Type 2

  • Projetar arquiteturas de dados em múltiplas camadas usando as camadas Bronze (ingestão bruta), Silver (processamento CDC) e Gold (pronta para analytics) com streaming tables e materialized views

  • Aplicar constraints abrangentes de qualidade de dados usando expectations do pipeline com ações WARN, DROP e FAIL para garantir a integridade dos dados nas operações de CDC

  • Processar arquivos JSON de streaming incrementalmente usando Auto Loader e gerenciar eventos do ciclo de vida do cliente (INSERT, UPDATE, DELETE), preservando versões históricas

  • Criar materialized views prontas para analytics que mantêm automaticamente os estados atuais dos clientes e rastreiam clientes removidos, para relatórios e business intelligence posteriores

CDC Pipeline Visão Geral

Nesta demonstração, você construirá um Apache Spark™ Declarative Pipeline que executa o fluxo medallion completo, desde a ingestão bruta até analytics curados:

  1. Ingerir arquivos JSON de origem do cloud storage em uma Bronze raw streaming table usando Auto Loader.
  2. Aplicar data quality expectations à tabela bruta para produzir uma tabela Bronze limpa, pronta para processamento posterior.
  3. Implementar a lógica CDC SCD Type 2 com AUTO CDC INTO para manter uma tabela Silver de clientes atualizada, com histórico completo de mudanças.
  4. Criar materialized views Gold para clientes atuais e clientes removidos, permitindo analytics e relatórios simplificados.

CREATE OR REFRESH STREAMING TABLE sdp_cdc_1_bronze.customers_bronze_raw_demo

C5. Aplique Regras de Qualidade de Dados à Tabela Bronze

Com os dados brutos JSON de CDC agora configurados para fazer streaming em sdp_cdc_1_bronze.customers_bronze_raw_demo, vamos adicionar mais uma camada de qualidade bronze antes de avançar para o Silver.

Você criará uma tabela intermediária sdp_cdc_1_bronze.customers_bronze_clean e aplicará constraints de qualidade de dados para filtrar e sinalizar registros inválidos, preservando valores NULL esperados para operações DELETE.

Nesta etapa, você vai:
- Aplicar múltiplas constraints para checar campos-chave.
- Usar ações WARN, DROP e FAIL para definir como as violações são tratadas.
- Adicionar lógica condicional e validação regex dentro das constraints.

Para detalhes, veja Manage data quality with pipeline expectations.

C5.1 - Sobre a Fonte de Dados

  • O feed de CDC contém operações INSERT, UPDATE e DELETE para registros de clientes.

  • Eventos INSERT e UPDATE incluem valores válidos para todas as colunas-chave.

  • Eventos DELETE têm valores NULL para todos os campos não-chave, como name, email, address, city e state.

Exemplo de um Registro Descartado:

address city customer_id email name operation state
NULL NULL 23617 NULL NULL DELETE NULL

C5.2 - Crie a Tabela Bronze Clean Usando Pipeline Data Quality Expectations

  1. Agora que temos uma compreensão geral dos dados, vamos definir as seguintes constraints de qualidade de dados que aplicam essas regras em uma tabela Bronze secundária chamada sdp_cdc_1_bronze.customers_bronze_clean_demo antes que os dados avancem para o estágio Silver.

Abaixo está uma tabela com as constraints de qualidade de dados:

Comment ID Constraint Rule / Expectation Violation Action Purpose
A valid_id customer_id IS NOT NULL FAIL Falha a transação se um registro estiver com customer_id ausente. Exigirá intervenção manual para correção.
B valid_operation operation IS NOT NULL DROP ROW Descarta qualquer registro sem um tipo de operation.
C valid_name name IS NOT NULL OR operation = "DELETE" WARN (default) Sinaliza valores ausentes de name, a menos que seja uma operação DELETE.
D valid_address All address fields (address, city, state, zip_code) must be non-null unless it's a DELETE WARN (default) Garante informações de endereço completas para eventos INSERT e UPDATE.
E valid_email email must match a valid format unless it's a DELETE DROP ROW Usa regex para validar o formato do email e descarta registros inválidos.
  1. Copie o código SQL abaixo e adicione ao final do seu arquivo cdc_pipeline.sql.



 ------------------------------------------------------
-- PASSO 2: Bronze Raw -> Bronze Clean
------------------------------------------------------
CREATE STREAMING TABLE sdp_cdc_1_bronze.customers_bronze_clean_demo
  (

    -- A. Exige um customer_id válido, falha a transação se ausente
    CONSTRAINT valid_id EXPECT (customer_id IS NOT NULL) 
      ON VIOLATION FAIL UPDATE,

    -- B. Exige uma operation válida, descarta qualquer registro com operation NULL
    CONSTRAINT valid_operation EXPECT (operation IS NOT NULL) 
      ON VIOLATION DROP ROW,

    -- C. Exige que name esteja presente, a menos que a operation seja DELETE
    CONSTRAINT valid_name EXPECT (name IS NOT NULL OR operation = "DELETE"),

    -- D. Exige campos de endereço completos, a menos que a operation seja DELETE
    CONSTRAINT valid_address EXPECT (
      (address IS NOT NULL 
       AND city IS NOT NULL 
       AND state IS NOT NULL 
       AND zip_code IS NOT NULL)
       OR operation = "DELETE"),

    -- E. Exige formato de email válido (regex), pula a checagem para DELETE, descarta linhas inválidas
    CONSTRAINT valid_email EXPECT (
      rlike(email, '^([a-zA-Z0-9_\\-\\.]+)@([a-zA-Z0-9_\\-\\.]+)\\.([a-zA-Z]{2,5})$') 
      OR operation = "DELETE") 
      ON VIOLATION DROP ROW
  )
  COMMENT "Limpa os dados bronze brutos e aplica constraints de qualidade"
AS 
SELECT 
  *,
  CAST(from_unixtime(timestamp) AS timestamp) AS timestamp_datetime -- Converte o unix timestamp
FROM STREAM sdp_cdc_1_bronze.customers_bronze_raw_demo;

Revise o código:

  • Esta query cria a tabela sdp_cdc_1_bronze.customers_bronze_clean_demo a partir da tabela sdp_cdc_1_bronze.customers_bronze_raw_demo.

  • Ela aplica as constraints de qualidade de dados definidas acima para garantir que apenas registros CDC válidos avancem para o próximo estágio antes de chegar ao Silver.

  • Também converte o UNIX timestamp para um timestamp legível usando CAST(from_unixtime(timestamp) AS timestamp) como timestamp_datetime.

C6. Implemente AUTO CDC INTO para a Tabela Silver

Agora que os dados da camada Bronze (sdp_cdc_1_bronze.customers_bronze_raw_demo -> sdp_cdc_1_bronze.customers_bronze_clean_demo) estão limpos, vamos criar uma tabela Silver que aplica automaticamente inserções, atualizações e exclusões à medida que novas mudanças chegam.

O problema: lógica de CDC manual é frágil

Em muitos pipelines, o Change Data Capture é implementado manualmente.

Isso geralmente significa escrever e manter uma instrução MERGE INTO que precisa lidar corretamente com:

  • Inserções, atualizações e exclusões
  • Eventos duplicados e replays
  • Mudanças que chegam atrasadas
  • Chaves e condições de match corretas

Mesmo quando o SQL parece simples, a lógica se torna fácil de quebrar à medida que os requisitos mudam.

Abordagem tradicional: exemplo manual com MERGE INTO

MERGE INTO target_table AS t
USING source_stream AS s
ON t.id = s.id
WHEN MATCHED AND s.operation = 'UPDATE'
  THEN UPDATE SET *
WHEN MATCHED AND s.operation = 'DELETE'
  THEN DELETE
WHEN NOT MATCHED AND s.operation = 'INSERT'
  THEN INSERT *

Por que isso é um problema

  • Você precisa manter a lógica de merge sozinho
  • Você precisa confiar nos valores de operation recebidos e tratar casos extremos
  • À medida que schemas evoluem e regras mudam, o merge frequentemente cresce para um grande bloco de SQL, difícil de testar e fácil de errar

A seguir, vamos substituir esse padrão por AUTO CDC INTO, que permite que o pipeline aplique mudanças de CDC automaticamente com muito menos código.

SOLUÇÃO

AUTO CDC INTO em Spark Declarative Pipelines simplifica esse processo, gerenciando automaticamente inserções, atualizações e exclusões em dados de streaming, reduzindo código boilerplate e melhorando a confiabilidade.

AUTO CDC INTO fornece as seguintes garantias e requisitos:

  • Realiza ingestão incremental e de streaming de dados de CDC
  • Permite definir um ou mais campos de chave primária para identificar registros
  • Assume por padrão que as linhas contêm inserções e atualizações
  • Opcionalmente aplica exclusões quando definido
  • Ordena registros que chegam atrasados usando uma sequencing key
  • Permite excluir colunas com a palavra-chave EXCEPT
  • Usa SCD Type 1 por padrão, embora vamos usar SCD Type 2 nesta demonstração

Vamos completar isso em duas etapas:

  1. Criar uma tabela target Silver vazia para armazenar dados históricos de clientes usando o padrão SCD Type 2
  2. Usar AUTO CDC INTO para aplicar automaticamente inserções, atualizações e exclusões à medida que novas mudanças chegam

NOTA: Para mais detalhes, veja a documentação oficial: The AUTO CDC APIs: Simplify change data capture with Apache Spark™ Declarative Pipelines

C6.2 - Realize SCD Type 2 com AUTO CDC INTO

  1. Antes de executarmos o AUTO CDC INTO, vamos observar mais de perto as colunas-chave da nossa tabela Bronze limpa (sdp_cdc_1_bronze.customers_bronze_clean_demo).

    Entender essas colunas ajuda a explicar como o Spark Declarative Pipelines detecta e aplica mudanças nas operações INSERT, UPDATE e DELETE.

    Abaixo está um preview simplificado dos dados. Incluímos apenas as colunas que são importantes para Change Data Capture (CDC).

customer_id (primary key) name email operation (type of change) timestamp_datetime (sequence column) source_file ...
23056 Brent Chavez nelsonjoy@example.com NEW 2021-09-23T17:26:21.000+00:00 00.json ...
23057 James Cruz perkinsdeborah@example.net UPDATE 2021-09-23T18:21:45.000+00:00 00.json ...
23058 Jennifer Christensen jmccullough@example.net DELETE 2021-09-23T00:19:44.000+00:00 00.json ...
... ... ... ... ... ... ...

Colunas-Chave

  • customer_id - Serve como a chave primária usada para identificar cada registro único de cliente. A lógica de CDC depende dessa coluna para determinar qual linha deve ser atualizada ou excluída na tabela target.

  • operation - Indica o tipo de mudança do sistema de origem (NEW, UPDATE ou DELETE).

  • Operações DELETE removem o registro correspondente da tabela target.

  • Operações NEW e UPDATE são processadas e mescladas automaticamente pelo AUTO CDC usando a coluna de chave primária customer_id.

  • timestamp_datetime - Define a ordem das operações. Isso garante que as atualizações sejam aplicadas na sequência correta quando múltiplas mudanças ocorrem para o mesmo registro.

  • source_file - Ajuda a rastrear de qual arquivo cada registro veio, útil para debugging e validação durante as execuções do pipeline.

Em seguida, usaremos essas colunas para realizar o AUTO CDC INTO, permitindo que o Spark Declarative Pipelines gerencie automaticamente as atualizações incrementais entre Bronze e Silver.

  1. O comando AUTO CDC INTO define um flow de Spark Declarative Pipeline que aplica a lógica de Change Data Capture SCD Type 2 para manter a tabela Silver continuamente atualizada.

Ele gerencia automaticamente como INSERTS, UPDATES e DELETES são aplicados entre o seguinte:

  • Source: sdp_cdc_1_bronze.customers_bronze_clean_demo - A tabela Bronze de streaming que contém os registros de CDC limpos.

  • Target: sdp_cdc_2_silver.customers_silver_scd2_demo - A tabela Silver que armazena os dados de clientes atuais e históricos.

    Copie e cole o código abaixo no seu arquivo cdc_pipeline.sql.



-- b. Realiza SCD Type 2 na tabela silver
CREATE FLOW customers_scd_type_2_flow AS 
AUTO CDC INTO sdp_cdc_2_silver.customers_silver_scd2_demo  -- Target: Onde os registros processados são armazenados
FROM STREAM sdp_cdc_1_bronze.customers_bronze_clean_demo   -- Source: Registros de CDC limpos da camada Bronze
  KEYS (customer_id)                                       -- Chave primária: usada para casar registros em updates/deletes
  APPLY AS DELETE WHEN operation = "DELETE"                -- Lógica de delete: remove registros marcados como DELETE
  SEQUENCE BY timestamp_datetime                           -- Ordenação: garante que as mudanças sejam aplicadas na sequência correta
  COLUMNS * EXCEPT (timestamp, _rescued_data, operation)   -- Seleção de colunas: inclui todas exceto campos de metadata
  STORED AS SCD TYPE 2;                                    -- SCD Type 2: mantém versões históricas com __START_AT e __END_AT

Revise o código

  • CREATE FLOW customers_scd_type_2_flow AS - Cria um flow nomeado (customers_scd_type_2_flow) que define como as mudanças de CDC serão processadas.
  • AUTO CDC INTO sdp_cdc_2_silver.customers_silver_scd2_demo - Aplica a lógica de CDC à tabela Silver target.
  • FROM STREAM sdp_cdc_1_bronze.customers_bronze_clean_demo - Lê os dados de origem de streaming que incluem novas inserções, atualizações e exclusões.
  • KEYS (customer_id) - Identifica o registro único de cliente pela sua chave primária.
  • APPLY AS DELETE WHEN operation = "DELETE" - Garante que registros com operação de exclusão sejam removidos do target.
  • SEQUENCE BY timestamp_datetime - Ordena os registros recebidos para que dados atrasados sejam processados corretamente.
  • COLUMNS * EXCEPT (timestamp, _rescued_data, operation) - Seleciona todas as colunas da origem, exceto campos de metadata ou de sistema.

  • STORED AS SCD TYPE 2 - Especifica o método Slowly Changing Dimension Type 2, que atualiza registros no local, mantendo versões históricas.

  • NOTA: Para mais informações, veja a documentação da Databricks AUTO CDC INTO (Apache Spark™ Declarative Pipelines).

  • __END_AT - Timestamp de quando o registro é encerrado (após uma atualização ou exclusão).

Detalhes do código - Isso identifica clientes removidos agrupando todas as versões, selecionando o registro mais recente de cada cliente e mantendo apenas aqueles marcados como excluídos, mostrando seus detalhes finais antes da remoção.

- **Use MAX_BY para encontrar o registro mais recente** - A função `MAX_BY(value, __START_AT)` retorna o valor da linha com o timestamp `__START_AT` mais recente.  
    - `MAX_BY(name, __START_AT)` - nome mais recente  
    - `MAX_BY(address, __START_AT)` - endereço mais recente  
    - `MAX_BY(__END_AT, __START_AT)` - marcador de exclusão mais recente do registro mais recente
    - etc.

- `GROUP BY customer_id` - Reúne todas as versões históricas de cada cliente em um único grupo, para que possamos analisar mudanças ao longo do tempo.

- `HAVING MAX_BY(__END_AT, __START_AT) IS NOT NULL` - Condição que mantém apenas clientes cujo registro mais recente tem um valor para `__END_AT`, significando que foram removidos.

- [função de agregação max_by](https://docs.databricks.com/aws/en/sql/language-manual/functions/max_by)

E. Crie Materialized Views Gold

Em vez de fazer com que os usuários consultem manualmente a tabela de CDC para encontrar clientes atuais ou excluídos, você pode criar materialized views Gold que expõem essa informação automaticamente como um objeto.

Essas views simplificam o acesso para usuários de negócio e podem ser adicionadas diretamente ao seu Spark Declarative Pipeline para atualizações contínuas.

Nesta etapa, criaremos duas views:

  • a. current_customers_gold_demo - Retorna apenas os registros de clientes ativos mais recentes (onde __END_AT IS NULL).

  • b. removed_customers_gold_demo - Cria uma Materialized View Gold que lista todos os clientes que foram removidos (excluídos) da tabela SCD Type 2. (Ela usa MAX_BY em múltiplas colunas, como name, address, city, state e zip_code, para retornar o registro mais recente por cliente onde o valor mais recente de __END_AT não é NULL.)

NOTAS:

  • Materialized views em Spark Declarative Pipelines fornecem uma camada atualizada automaticamente para relatórios e dashboards. Elas facilitam consultar apenas o estado atual dos clientes ou identificar clientes removidos sem varrer todo o histórico de SCD.

  • Quando possível, materialized views são atualizadas incrementalmente. Para mais informações, veja Incremental refresh for materialized views.

E1. Crie a Materialized View de Clientes Atuais

  1. Copie e cole o código abaixo no seu arquivo cdc_pipeline.sql para criar suas materialized views gold. Explore o código.



---------------------------------------------------------------------------------------
-- PASSO 4: Criar Materialized View para Clientes Atuais (Ativos)
---------------------------------------------------------------------------------------

-- a. Cria a Materialized View Gold para Clientes Atuais
CREATE OR REFRESH MATERIALIZED VIEW sdp_cdc_3_gold.current_customers_gold_demo
COMMENT "Lista atualizada de clientes ativos"
AS 
SELECT 
  * EXCEPT (processing_time),
  current_timestamp() updated_at
FROM sdp_cdc_2_silver.customers_silver_scd2_demo
WHERE `__END_AT` IS NULL;      -- Filtra apenas linhas com valor nulo para __END_AT, o que indica a versão atual do registro

E2. Crie a Materialized View de Clientes Excluídos

  1. Copie e cole o código abaixo no seu arquivo cdc_pipeline.sql para criar suas materialized views gold. Explore o código.

  2. NOTA: Como isso usa GROUP BY com agregações em vez de window functions, o Lakeflow pode atualizar a view incrementalmente à medida que novos dados de CDC chegam, em vez de recomputar tudo.



-- b. Cria a Materialized View Gold que lista todos os clientes que foram removidos (excluídos) da tabela SCD Type 2.
CREATE OR REFRESH MATERIALIZED VIEW sdp_cdc_3_gold.removed_customers_gold_demo AS
SELECT
  customer_id,
  MAX_BY(name, __START_AT)      AS name,
  MAX_BY(address, __START_AT)   AS address,
  MAX_BY(city, __START_AT) AS city,
  MAX_BY(state, __START_AT)   AS state,
  MAX_BY(zip_code, __START_AT)   AS zip_code,
  MAX_BY(__START_AT, __START_AT) AS __START_AT,
  MAX_BY(__END_AT, __START_AT)  AS __END_AT
FROM sdp_cdc_2_silver.customers_silver_scd2_demo
GROUP BY customer_id
HAVING MAX_BY(__END_AT, __START_AT) IS NOT NULL;  -- Encontra o valor __END_AT do registro mais recente e retorna apenas se não for nulo
