Aula — Revisão de Change Data Capture (CDC)

Esta aula fornece uma revisão abrangente dos conceitos de Change Data Capture (CDC) e padrões de implementação no Lakehouse. Você vai explorar como CDC permite sincronização eficiente de dados, entender os padrões SCD Type 1 e Type 2, e ver como AUTO CDC INTO simplifica a implementação em Spark Declarative Pipelines.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de: - Explicar o que é CDC e como ele mantém dados sincronizados entre sistemas - Descrever SCD Type 1 (sobrescrita) e SCD Type 2 (histórico) - Implementar CDC usando AUTO CDC INTO em Spark Declarative Pipelines

A. O que é Change Data Capture?

Change Data Capture (CDC) é uma técnica que identifica e captura mudanças feitas nos dados em um sistema fonte (inserts, updates, deletes) e então aplica essas mudanças a um sistema target, mantendo-o sincronizado.

EXPANDIR PARA NOTAS ADICIONAIS
Vamos revisar **Change Data Capture (CDC)**, um conceito fundamental para manter dados sincronizados entre sistemas. #### Definição e Propósito do CDC Change Data Capture é uma técnica que rastreia e captura mudanças de dados conforme acontecem em um sistema fonte. Em vez de recarregar datasets inteiros, CDC identifica e propaga apenas as mudanças, tornando a sincronização de dados significativamente mais eficiente. #### Benefícios-Chave: - **Eficiência**: Processa apenas mudanças, não datasets inteiros - **Tempo real**: Captura mudanças conforme acontecem - **Auditabilidade**: Mantém registro de todas as mudanças - **Consistência**: Garante que sistemas target reflitam o estado atual da fonte

B. Slowly Changing Dimensions (SCD) Type 1

B1. SCD Type 1 - Visão Geral

SCD Type 1 atualiza a tabela target sobrescrevendo linhas existentes com os valores mais recentes. Nenhum histórico de versão é mantido — apenas o estado atual é preservado.

EXPANDIR PARA NOTAS ADICIONAIS
SCD Type 1 atualiza a **tabela target** **sobrescrevendo linhas existentes** com os valores mais recentes. Nenhum histórico de versão é mantido — apenas o estado atual é armazenado. #### Operações: - **INSERT**: Registros novos são adicionados - **UPDATE**: Registros existentes são sobrescritos com novos valores - **DELETE**: Registros são removidos #### Quando usar SCD Type 1: - Quando o histórico não é necessário - Para dados de referência que mudam raramente - Para correções de dados (ex: corrigir erro de digitação)

B2. SCD Type 1 - Exemplo de Implementação

Quando aplicamos SCD Type 1, a tabela target é atualizada com as informações mais recentes do cliente usando o CustomerID (coluna chave) e ProcessDate (coluna de sequência). O registro mais recente pelo ProcessDate sempre vence.

EXPANDIR PARA NOTAS ADICIONAIS
Quando aplicamos **SCD Type 1**, a tabela target é atualizada com as informações mais recentes usando o **CustomerID** (coluna chave) e **ProcessDate** (coluna de sequência). #### O que acontece: - Peter (ID 001): múltiplos updates → valor mais recente pelo ProcessDate vence - Samarth (ID 002): marcado como DELETE → removido da tabela target - Kostas (ID 003): novo registro → inserido na tabela target

C. Slowly Changing Dimensions (SCD) Type 2

C1. SCD Type 2 - Cenário

SCD Type 2 preserva todas as versões de um registro adicionando colunas de metadata (__START_AT, __END_AT). A versão ativa tem __END_AT = null.

C2. SCD Type 2 - Implementação

SCD Type 2 introduz rastreamento histórico e versionamento de registros, preservando uma trilha de auditoria completa de todas as mudanças ao longo do tempo.

EXPANDIR PARA NOTAS ADICIONAIS
**Slowly Changing Dimensions Type 2 (SCD Type 2)** introduz **rastreamento histórico e versionamento** de registros, preservando uma trilha de auditoria completa. #### Colunas de Metadata: - `__START_AT` — quando a versão se tornou ativa - `__END_AT` — quando a versão se tornou inativa (null = versão atual ativa) #### Operações: - **INSERT**: Nova linha com `__START_AT = data_evento`, `__END_AT = null` - **UPDATE**: Linha antiga recebe `__END_AT = data_evento`, nova linha com `__END_AT = null` - **DELETE**: Linha recebe `__END_AT = data_evento` mas é mantida para histórico

D. Implementando CDC com AUTO CDC INTO em Spark Declarative Pipelines (Exemplo SCD Type 1)

AUTO CDC INTO simplifica a implementação de CDC com sintaxe declarativa — substitui lógica complexa de MERGE INTO.

AUTO CDC INTO target_table
FROM source_stream
KEYS (customer_id)
APPLY AS DELETE WHEN operation = 'DELETE'
SEQUENCE BY process_date
COLUMNS *
STORED AS SCD TYPE 1;
EXPANDIR PARA NOTAS ADICIONAIS
Agora que cobrimos os conceitos de CDC e ambos os padrões SCD, vamos explorar como **Apache Spark™ Declarative Pipelines** simplifica a implementação de CDC com o statement `AUTO CDC INTO`: #### Cada cláusula explicada: - **AUTO CDC INTO target_table** — Tabela target onde as mudanças serão aplicadas - **FROM source_stream** — Fonte streaming com os change events - **KEYS (customer_id)** — Colunas para match entre fonte e target (primary key) - **APPLY AS DELETE WHEN** — Condição que identifica deletes - **SEQUENCE BY process_date** — Ordena mudanças cronologicamente (mais recente vence) - **COLUMNS *** — Quais colunas aplicar (* = todas) - **STORED AS SCD TYPE 1** — Tipo de SCD (1 = overwrite, 2 = versionamento)

F. Resumo e Pontos-Chave

O que abordamos:

  1. Change Data Capture (CDC) permite sincronização automatizada de mudanças de dados entre sistemas
  2. SCD Type 1 sobrescreve dados existentes, mantendo apenas o estado atual
  3. SCD Type 2 mantém histórico completo através de rastreamento de versões com datas de início e fim
  4. AUTO CDC INTO simplifica a implementação de CDC com sintaxe declarativa, eliminando a necessidade de lógica complexa de MERGE INTO
  5. A cláusula SEQUENCE BY garante a ordem correta de processamento quando há múltiplas mudanças para o mesmo registro

F. Resumo e Pontos-Chave

O que abordamos:

  1. Change Data Capture (CDC) enables automated synchronization of data changes between systems
  2. SCD Type 1 overwrites existing data, maintaining only current state (no history)
  3. SCD Type 2 preserves complete historical versions using metadata columns
  4. AUTO CDC INTO provides declarative, simplified CDC implementation in Lakeflow pipelines

Decision Framework:

Choose SCD Type 1 when: - Only current data state is needed - Storage efficiency is prioritized - Historical tracking is not required

Choose SCD Type 2 when: - Historical analysis is essential - Audit trails are required for compliance - Point-in-time reporting is needed
