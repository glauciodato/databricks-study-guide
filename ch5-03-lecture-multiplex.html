Aula — Introdução a Multiplex Streaming, Delta Sinks e Iceberg Reads

Esta aula apresenta três conceitos avançados usados em Spark Declarative Pipelines: o padrão Multiplex para streaming multi-event eficiente, Delta Sinks para escrever em tabelas externas, e Iceberg Reads via Delta UniForm para interoperabilidade cross-platform.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de: - Explicar o padrão Multiplex e como ele resolve ingestão multi-event - Descrever como Delta Sinks escrevem dados para fora do pipeline - Explicar como Delta UniForm habilita leitura cross-platform via Iceberg - Conectar os três conceitos em um padrão de pipeline completo

A. O Padrão Multiplex

O padrão Multiplex endereça um desafio comum de produção: processar eficientemente múltiplos tipos de eventos que chegam por um único mecanismo de transporte de dados.

A1. O Problema: Um Stream, Muitos Schemas

Em ambientes de produção, múltiplos sistemas de negócios frequentemente compartilham um único transporte de dados como: - Um tópico Kafka - Um caminho de cloud storage - Um endpoint de streaming API

Os dados que chegam contêm múltiplos tipos de eventos (pedidos, devoluções, cliques, etc.), cada um com seu próprio schema. Processar cada tipo de evento separadamente na fonte é custoso e frágil — o padrão Multiplex resolve isso.

A2. Ingerir Uma Vez, Distribuir por Tipo

O padrão Multiplex segue uma abordagem simples mas poderosa:

  1. Ingestão Única: Ler todos os tipos de eventos em uma bronze table
  2. Filtragem por Tipo: Usar queries filtradas para separar por tipo de evento
  3. Tabelas Especializadas: Cada tipo de evento vai para sua própria silver table

Isso é chamado de "fan out" — um único stream de entrada se divide em múltiplos streams especializados baseados no tipo de evento.

Vantagens: Uma única ingestão (eficiente), processamento isolado por tipo (robusto), schema evolution independente por tabela.

B. Sinks

Sinks fornecem um mecanismo para escrever dados streaming de um Spark Declarative Pipeline para Delta tables externas que existem fora do escopo gerenciado do pipeline.

Todo dataset padrão em um Spark Declarative Pipeline — streaming table ou materialized view — é possuído e gerenciado pelo pipeline. Isso significa que o pipeline controla o ciclo de vida da tabela: criação, atualizações e exclusão.

Um sink quebra essa relação — ele escreve dados para uma tabela que existe independentemente do pipeline. O pipeline escreve, mas não possui.

B1. Tipos de Sink Suportados

O Databricks suporta quatro tipos de sinks — cada um adequado para um destino e caso de uso diferente.

Tipo de Sink Destino Caso de Uso
Delta Sink Delta table externa Tabelas que precisam existir fora do lifecycle do pipeline
Kafka Sink Tópico Kafka Streaming de eventos para sistemas downstream
Unity Catalog Sink UC table Tabelas gerenciadas no Unity Catalog
Event Hubs Sink Azure Event Hubs Streaming para Azure Event Hubs

B2. Tabelas Gerenciadas vs. Sinks

Todo dataset padrão em um Spark Declarative Pipeline — streaming table ou materialized view — é possuído e gerenciado pelo pipeline. Um sink quebra essa relação intencionalmente — ele escreve dados para uma tabela que existe independentemente do pipeline.

Aspecto Tabela Gerenciada Sink
Lifecycle Pipeline cria, atualiza e pode deletar Tabela existe independentemente
Propriedade Pipeline é o owner Outro processo ou equipe é o owner
Drop on delete Pode ser deletada quando pipeline é removido Nunca é afetada pela remoção do pipeline
Configuração Limitada ao que o pipeline suporta Configuração completa da tabela externa

B3. Delta Sink em Ação

Um Delta sink escreve output do pipeline para uma Delta table fora do lifecycle gerenciado do pipeline — habilitando configurações não possíveis em tabelas gerenciadas.

-- Criar a tabela externa primeiro
CREATE TABLE IF NOT EXISTS catalog.schema.external_orders (
  order_id STRING,
  total DECIMAL(10,2),
  order_date DATE
) USING DELTA;

-- Criar o sink que escreve nela
CREATE SINK orders_external_sink
AS INSERT INTO catalog.schema.external_orders BY NAME
SELECT order_id, total, order_date
FROM STREAM orders_silver;

Pontos-chave: A tabela target deve existir antes de criar o sink. O sink processa incrementalmente (apenas dados novos). A tabela externa pode ter suas próprias configurações (Liquid Clustering, particionamento, etc.).

C. Iceberg Reads via Delta UniForm

Delta UniForm permite acesso cross-platform a Delta tables gerando automaticamente metadata Apache Iceberg sem duplicar os dados subjacentes.

C1. O Desafio Cross-Platform

Arquiteturas de dados modernas abrangem múltiplas plataformas. Tradicionalmente, suportar cada plataforma significava duplicar dados em formatos diferentes — caro, complexo e propenso a inconsistências.

Delta UniForm resolve isso mantendo um único dataset físico com metadata em múltiplos formatos — Delta e Iceberg. Ferramentas que leem Iceberg (Snowflake, Trino, Presto, Apache Flink) podem acessar a mesma tabela Delta sem cópia de dados.

C2. Como Delta UniForm Funciona

Delta UniForm mantém um dataset físico com duas visões lógicas — sem duplicação de dados, sem cópias separadas. Metadata Iceberg é gerada automaticamente pelo Delta Lake.

-- Habilitar UniForm ao criar a tabela
CREATE TABLE IF NOT EXISTS catalog.schema.orders_uniform
TBLPROPERTIES (
  'delta.universalFormat.enabledFormats' = 'iceberg'
)
AS SELECT * FROM orders_gold;

Para ler de dentro de um Spark Declarative Pipeline:

-- Ler tabela Iceberg dentro do pipeline
CREATE OR REFRESH MATERIALIZED VIEW iceberg_analysis
AS SELECT * FROM iceberg_catalog.schema.table_name;

Pontos-chave: Sem duplicação de dados. Metadata Iceberg é gerada automaticamente. Qualquer ferramenta compatível com Iceberg pode ler a tabela.

EXPANDIR PARA DETALHES ADICIONAIS

Delta UniForm (Universal Format) resolve um problema antigo no ecossistema lakehouse: diferentes motores de processamento usam diferentes formatos de tabela. Com UniForm, você escreve uma vez em Delta e leitores Iceberg/Hudi acessam a mesma tabela — sem ETL adicional, sem cópias, sem inconsistências.

D. Conectando os Conceitos

Esses três conceitos trabalham juntos para resolver requisitos complexos de data pipelines no mundo real. Cada conceito resolve um problema distinto. Juntos formam um padrão completo para construir streaming pipelines de nível de produção.

Conceito Problema que Resolve Solução
Multiplex Múltiplos tipos de eventos em uma fonte Ingestão única, fan out por tipo
Delta Sink Precisa escrever fora do pipeline Tabela externa não gerenciada pelo pipeline
Delta UniForm/Iceberg Acesso cross-platform Metadata Iceberg gerada automaticamente

D. Connecting the Concepts

These three concepts work together to solve complex do mundo real data pipeline requirements.Each concept solves a distinct problem. Together they form a complete pattern for pipelines that need real-time processing and cross-platform access.
