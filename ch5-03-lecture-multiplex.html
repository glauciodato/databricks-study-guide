Lecture - Introduction to Multiplex Streaming, Delta Sinks, and Iceberg Reads

Esta aula apresenta three advanced concepts used in Spark Declarative Pipelines: the Multiplex pattern for efficiently ingesting mixed event streams, Delta Sinks for writing streaming data to external tables, and Iceberg reads via Delta UniForm for enabling acesso cross-platform to Delta tables.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de:

  • Explain the Multiplex pattern and how fan-out works for mixed event streams
  • Describe what a Delta Sink is and when to use it over managed streaming tables
  • Explain how Delta UniForm enables Iceberg reads sem duplicação de dados
  • Understand how these three concepts chain together in a single pipeline

A. The Multiplex Pattern

The Multiplex pattern addresses a common production challenge: efficiently processing múltiplos tipos de eventos that arrive through um único transporte de dados mechanism.

A1. The Problem: One Stream, Many Schemas

Em ambientes de produção, multiple business systems often share a single data transport como por exemplo: - One Kafka topic - One cloud storage path
- One message queue

Each message carries a type field identifying which business domain it belongs to. Without the Multiplex pattern, this creates significant operational overhead:

Without Multiplex
  • N event types → N separate pipelines
  • N separate checkpoints and source scans
  • Source change must be applied N times
With Multiplex
  • N event types → 1 ingestion pipeline
  • 1 checkpoint, 1 source scan shared across all domains
  • Source change applied in one place

Reference Documentation: - Multiplexing Data Pipelines Blog

A2. Ingest Once, Fan Out by Type

The Multiplex pattern follows a simple but powerful approach:

  1. Single Ingestion: Read all event types into one bronze table
  2. Type-Based Filtering: Use the event type field to separate domains
  3. Fan-Out Processing: Create domain-specific tables downstream

B. Sinks

Sinks provide a mechanism to write streaming data from a Spark Declarative Pipeline to external Delta tables that exist fora do pipeline's managed scope.

Only the Python API is supported — SQL is not supported for sinks. Only append_flow can write to a sink.

B1. Supported Sink Types

Databricks supports four types of sinks — each suited for a different destination and use case.

Delta Table Sink
  • Unity Catalog managed tables
  • External Delta tables
  • Write by path or table name
Apache Kafka Sink
  • Write back to Kafka topics
  • Low-latency operational use cases
  • Reverse ETL out of Databricks
Azure Event Hubs Sink
  • Uses Kafka interface format
  • Real-time event streaming
  • Fraud detection · recommendations
Python Custom Sink
  • Write to any data store
  • Uses PySpark custom data sources
  • Maximum flexibility
For code examples of each sink type, refer to the Creating a Sink Documentation

B2. Managed Tables vs. Sinks

Every standard dataset in a Spark Declarative Pipeline — streaming table or materialized view — is owned and managed by the pipeline. A sink breaks this intentionally: it lets the pipeline write streaming data to a plain Delta table that exists fora do pipeline's managed scope.

Managed Table (Default)
  • Data stays within Unity Catalog
  • Full pipeline lineage tracking
  • Supports expectations and CDC
  • Streaming Tables and Materialized Views
vs
Sink
  • Write to external systems outside Databricks
  • Enables reverse ETL and operational use cases
  • Supports Kafka, Event Hubs, custom targets
  • No expectations — append only

B3. Delta Sink In Action

A Delta sink writes pipeline output to a Delta table outside the pipeline's managed lifecycle — unlocking configurations not possible on pipeline-managed streaming tables, such as Iceberg compatibility.

Streaming Tables Cannot
  • Enable Iceberg compatibility
  • Share with non-Databricks platforms
Delta Sink Can
  • Have full Delta table property control
  • Enables Iceberg UniForm for cross-platform reads

Implementation

Step 1 — Register the Sink

from pyspark import pipelines as dp

dp.create_sink(
    name    = "my_sink",
    format  = "delta",
    options = {
        "tableName": "catalog.schema.table"
    }
)
→
Step 2 — Write to the Sink



@dp.append_flow(
name   = "my_sink_flow",
target = "my_sink"
)
def my_sink_flow():
    return spark.readStream.table(
        "schema.source_table"
    )
  • Checkpointing is handled automatically by append_flow
  • Only new records written per run — no overwrites
  • Python only — no SQL equivalent

C. Iceberg Reads via Delta UniForm

Delta UniForm enables acesso cross-platform to Delta tables by automatically generating Apache Iceberg metadata sem duplicar os dados subjacentes.

C1. The Cross-Platform Challenge

Modern data architectures span multiple platforms. Traditionally, supporting each platform meant copying data into multiple formats — creating duplication, sync issues, and increased storage costs. Delta UniForm solves this with a single set of files and two metadata layers.

C2. How Delta UniForm Works

Delta UniForm maintains one physical dataset with two logical views — no data duplication, no separate copies. Iceberg metadata is generated asynchronously after every Delta write, keeping both views in sync automatically.

Enabling Iceberg Reads

1️⃣
Disable Deletion Vectors
Property: 'delta.enableDeletionVectors' = 'false'
Iceberg v2 cannot represent Delta's soft-delete markers. Disabling ensures all deletes are hard deletes, making the table fully readable by Iceberg clients.
2️⃣
Column Mapping Mode
Property: 'delta.columnMapping.mode' = 'name'
Ensures column identifiers are consistent between Delta and Iceberg schemas, preventing schema drift and enabling seamless acesso cross-platform.
3️⃣
Enable IcebergCompatV2
Property: 'delta.enableIcebergCompatV2' = 'true'
Activates Delta's write protocol compatible with Iceberg v2, allowing Iceberg clients to read Delta tables without data conversion.
4️⃣
Enable Universal Format
Property: 'delta.universalFormat.enabledFormats' = 'iceberg'
Triggers asynchronous Iceberg metadata generation after every Delta commit, ensuring up-to-date Iceberg views for external tools.
⚠️ Iceberg Reads Only Work on Plain Delta Tables
Note: Pipeline-managed streaming tables and materialized views cannot have Iceberg reads enabled. Only a plain external Delta table—such as one created via a Delta Sink—supports UniForm. This bridge is required for acesso cross-platform.

Detalhes Adicionais: Setting these properties is a one-time operation, but must be done before any data is written. Once enabled, Iceberg metadata is kept in sync automatically, allowing tools like Snowflake, Trino, and Athena to query the same Delta table.
For more details refer to the Delta UniForm Documentation

EXPANDIR PARA DETALHES ADICIONAIS

Delta UniForm (Universal Format) solves a long-standing problem in the lakehouse ecosystem: different tools speak different table formats. Snowflake, Trino, Athena, and open-source Spark all understand Apache Iceberg — but not Delta Lake natively. UniForm bridges this gap by making your Delta tables simultaneously readable as Iceberg tables, without any data duplication or separate pipelines.
Both Delta Lake and Apache Iceberg are built on the same foundation: Parquet data files plus a metadata layer. UniForm exploits this by asynchronously generating Iceberg metadata after every Delta write — the same Parquet files now serve two formats at once. From a Delta client's perspective, nothing changes. From an Iceberg client's perspective, it looks like a native Iceberg table. You get one dataset, two logical views, zero duplication.
--- #### Benefits
- No data movement: A single copy of Parquet files is shared across Delta and Iceberg clients — no ETL, no replication, no storage overhead. - Cross-platform interoperability: Tools like Snowflake, Trino, Apache Athena, and open-source Spark can query your Delta tables directly via the Iceberg REST Catalog. - Negligible write overhead: Iceberg metadata generation happens asynchronously after the Delta commit, so your write pipelines are not slowed down. - Works with Unity Catalog: Unity Catalog acts as the Iceberg REST Catalog, meaning external clients get governed, catalogued access without any extra infrastructure. - Performance parity: Benchmarks show comparable read performance between Delta UniForm and natively managed Iceberg tables on Snowflake.
--- #### Limitations
- Read-only for Iceberg clients: External tools can only read via Iceberg. All writes must go through Delta — you cannot write to a UniForm table from Snowflake or Trino. - Deletion Vectors must be disabled: Tables using deletion vectors (a Delta performance feature) cannot have UniForm enabled. You must set 'delta.enableDeletionVectors' = 'false'. - Streaming Tables and Materialized Views are excluded: Pipeline-managed tables in Spark Declarative Pipelines cannot have the required delta.universalFormat.enabledFormats property set directly. This is where Delta Sinks come in — they write to plain external Delta tables where UniForm can be freely enabled. - Column mapping is permanent: Enabling UniForm also enables column mapping (delta.columnMapping.mode = 'name'), which cannot be dropped once set. - Databricks Runtime 14.3 LTS or above required: Any Databricks client writing to a UniForm-enabled table must use DBR 14.3+. - Table must be accessed by name: Iceberg metadata generation is only triggered when the table is accessed by name (not by path).
---
🔗 How this connects to Delta Sinks: Since Streaming Tables and Materialized Views can't use UniForm directly, the pattern in this lecture is to use a Delta Sink — write your streaming pipeline output to a plain external Delta table, enable UniForm on that table, and Iceberg clients can immediately read it. This is the recommended production pattern for cross-platform Iceberg access from a live streaming pipeline.
