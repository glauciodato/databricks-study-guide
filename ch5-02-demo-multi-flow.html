Demo - Multi Flow SDP com Liquid Clustering e Data Quality

Visão Geral

Esta demonstração mostra como construir um pipeline de dados incremental robusto usando Apache Spark™ Declarative Pipelines (SDP) para consolidar dados de múltiplas subsidiárias (fontes de dados) em uma única target streaming table.

Você trabalhará com três subsidiárias fictícias de uma empresa: Bright Home, Lumina Sports e Northstar Outfitters, cada uma produzindo dados de transação em formatos diferentes (CSV e JSON). A demo ilustra como superar desafios comuns de pipeline, incluindo múltiplos flows escrevendo em uma única tabela, incompatibilidades de schema, problemas de qualidade de dados e requisitos de otimização de performance.

Através de implementação prática, você criará um pipeline completo de arquitetura medallion que ingere incrementalmente múltiplas fontes de dados em uma única tabela bronze usando flows, aplica constraints de qualidade de dados e transformações na camada silver com otimização via liquid clustering, e cria materialized views de business intelligence na camada gold.

Objetivos de Aprendizado

Ao final desta demonstração, você será capaz de: - Ingerir múltiplas fontes de dados em uma tabela bronze usando Spark Declarative Pipelines com diferentes formatos de arquivo, como CSV e JSON.

  • Padronizar schemas na camada bronze e mapear os tipos de dados corretos na camada silver para resolver diferenças entre sistemas de origem.

  • Adicionar checagens de qualidade de dados e habilitar liquid clustering nas tabelas silver para aplicar regras básicas e melhorar a performance de queries.

  • Construir materialized views incrementais na camada gold que atualizam automaticamente e fornecem analytics prontos para uso.

  • Executar e monitorar a execução completa do pipeline em bronze, silver e gold, incluindo cargas incrementais e rastreamento de data lineage.

Multi Flow Pipeline Demonstration Visão Geral

Nesta demonstração, você construirá um Apache Spark™ Declarative Pipeline que executa o fluxo medallion completo, desde a ingestão bruta de múltiplas fontes de dados até analytics curados

  1. Usar múltiplos flows (3) para ingerir incrementalmente arquivos de três locais de cloud storage e escrever em uma única tabela bronze.
    • Cada volume é uma remessa diária de pedidos de uma subsidiária específica que a empresa possui. Queremos que todos esses dados sejam ingeridos em uma única tabela para análise geral.
  2. Definir e construir a tabela silver com um schema limpo, aplicar constraints básicas de qualidade de dados e habilitar liquid clustering para performance de queries à medida que os dados continuam crescendo.
  3. Criar materialized views gold que atualizam automaticamente e fornecem analytics prontos para uso.

Objetivo: Ingerir Todos os Arquivos de Origem Brutos em uma Única Tabela Bronze Streaming

Para combinar com sucesso as três fontes em uma única bronze streaming table, precisaremos padronizar o schema.

Para isso, vamos ingerir todas as colunas como STRING na tabela bronze.

Isso evita conflitos de tipos de dados entre arquivos CSV e JSON, já que cada formato infere tipos de forma diferente. Normalizar tudo para STRING mantém a camada bronze previsível, evita falhas de ingestão e nos permite aplicar os tipos de dados corretos posteriormente na camada silver.

D. Usando Múltiplos Flows para Escrever em um Único Target

Em muitos ambientes corporativos, os dados chegam de vários sistemas que precisam ser consolidados em uma única tabela para processamento posterior.

Neste exemplo, a empresa tem três subsidiárias, cada uma produzindo dados de transação em formatos de arquivo bruto ligeiramente diferentes.

Com Spark Declarative Pipelines, você pode definir múltiplos flows que escrevem na mesma target streaming table, permitindo que todos os arquivos brutos no cloud storage sejam ingeridos incrementalmente em um único destino unificado.

D1. Crie a Tabela Target Bronze

  1. Comece criando a bronze streaming table que servirá como landing zone para todos os dados de transação recebidos.

    Esta tabela ingere todas as colunas como STRING para garantir compatibilidade entre os diferentes sistemas de origem.

    Copie o código SQL abaixo e cole no seu arquivo flow_ingestion.sql.


------------------------------------------
-- CRIAR A ESTRUTURA DA TABELA BRONZE
------------------------------------------
CREATE OR REPLACE STREAMING TABLE multi_flow_1_bronze.orders_bronze_flows_demo
(
  subsidiary_id   STRING,
  order_id        STRING,
  order_timestamp STRING,
  customer_id     STRING,
  region          STRING,
  country         STRING,
  city            STRING,
  channel         STRING,
  sku             STRING,
  category        STRING,
  qty             STRING,
  unit_price      STRING,
  discount_pct    STRING,
  coupon_code     STRING,
  total_amount    STRING,
  order_date      STRING,
  source_file     STRING,   -- Adicionada pela coluna _metadata para retornar o nome do arquivo de origem
  file_mod_time   TIMESTAMP -- Adicionada pela coluna _metadata para retornar o horário de modificação do arquivo. Retorna um valor consistente
)
COMMENT "Cria uma única tabela bronze streaming com pedidos de todas as subsidiárias usando múltiplos flows."
TBLPROPERTIES (
  'pipelines.reset.allowed' = false    -- impede refreshes completos na tabela bronze
);

Revise o código - A cláusula COMMENT adiciona metadados descritivos à tabela para fins de documentação.

  • A instrução TBLPROPERTIES configura a seguinte definição:
  • Proteção contra Reset: A propriedade 'pipelines.reset.allowed' = false impede refreshes completos na streaming table, o que ajuda a evitar a remoção acidental de checkpoints e a truncagem dos dados da streaming table.

IMPORTANTE: Entendendo a Proteção contra Full Table Refresh

Essa proteção é particularmente importante quando sua fonte de dados bruta remove arquivos automaticamente após um determinado período. Sem essa configuração, dados que não estão mais presentes no diretório de origem não seriam reingeridos na target table durante uma operação de Run pipeline with full table refresh.

NOTA: Para orientações sobre quando usar full refreshes, consulte a documentação Should I use a full refresh?.

D3. Configure o Flow a partir do Volume Bright Home Orders

  1. Copie o código abaixo e cole no seu arquivo flow_ingestion.sql.



------------------------------------------
-- FLOW BRONZE - BRIGHT HOME
------------------------------------------
-- Lê arquivos CSV do volume bright_home_orders
CREATE FLOW bright_home_orders_flow
AS INSERT INTO multi_flow_1_bronze.orders_bronze_flows_demo BY NAME
SELECT
  CAST(subsidiary_id AS STRING) AS subsidiary_id,
  CAST(order_id AS STRING) AS order_id,
  CAST(order_timestamp AS STRING) AS order_timestamp,
  CAST(customer_id AS STRING) AS customer_id,
  CAST(region AS STRING) AS region,
  CAST(country AS STRING) AS country,
  CAST(city AS STRING) AS city,
  CAST(channel AS STRING) AS channel,
  CAST(sku AS STRING) AS sku,
  CAST(category AS STRING) AS category,
  CAST(qty AS STRING) AS qty,
  CAST(unit_price AS STRING) AS unit_price,
  CAST(discount_pct AS STRING) AS discount_pct,
  CAST(coupon_code AS STRING) AS coupon_code,
  CAST(total_amount AS STRING) AS total_amount,
  CAST(order_date AS STRING) AS order_date,
  _metadata.file_name AS source_file,
  _metadata.file_modification_time AS file_mod_time
FROM STREAM read_files(
    '${bright_home_orders_source}',   -- Usa o parâmetro de configuração para apontar para o volume bright_home_orders
    format => 'csv',
    header => true
);

Revise o código - Todas as colunas de negócio são convertidas para STRING para que este flow se alinhe ao schema bronze unificado, enquanto as colunas de metadata mantêm seus tipos nativos.
- As colunas de metadata capturam o nome do arquivo e o horário de modificação de origem, o que ajuda com lineage e debugging.
- A cláusula FROM STREAM read_files('${bright_home_orders_source}', ...) usa seu parâmetro de configuração para referenciar o caminho do volume e depende do Auto Loader para ingestão incremental.

E2. Crie a Tabela Silver de Transações com Liquid Clustering e Regras de Qualidade de Dados

  1. Adicione o código a seguir ao seu arquivo silver_transformation.sql para criar uma tabela Silver com:
  2. um schema definido,
  3. tipos de coluna consistentes aplicados via TRY_CAST
  4. e liquid clustering habilitado para performance



CREATE OR REFRESH STREAMING TABLE multi_flow_2_silver.orders_silver_flows_demo
(
  -- A: Define um schema fixo para prevenir evolução de schema.
  subsidiary_id   STRING,
  order_id        STRING,
  order_timestamp TIMESTAMP,
  order_date      DATE,
  customer_id     STRING,
  region          STRING,
  country         STRING,
  city            STRING,
  channel         STRING,
  sku             STRING,
  category        STRING,
  qty             INT,
  unit_price      DOUBLE,
  discount_pct    DOUBLE,
  total_amount    DOUBLE,
  coupon_code     STRING,

  -- B: Constraints de qualidade de dados para descartar ou sinalizar linhas inválidas.
  CONSTRAINT qty_valid          EXPECT (qty >= 0) ON VIOLATION DROP ROW,
  CONSTRAINT total_amount_valid EXPECT (total_amount >= 0) ON VIOLATION DROP ROW,
  CONSTRAINT timestamp_not_null EXPECT (order_timestamp IS NOT NULL) ON VIOLATION FAIL UPDATE
)
-- C: Adiciona um comentário na tabela
COMMENT 'Limpa e padroniza dados da tabela bronze de múltiplos flows'

-- D: Habilita liquid clustering para melhorar a performance em filtros comuns.
CLUSTER BY AUTO

AS
-- E: Seleciona e limpa dados da tabela Bronze. Usa TRY_CAST para garantir tipos consistentes entre todas as subsidiárias.
SELECT
  subsidiary_id,
  order_id,
  TRY_CAST(order_timestamp AS TIMESTAMP) AS order_timestamp, 
  TRY_CAST(order_date      AS DATE)      AS order_date,
  customer_id,
  region,
  country,
  city,
  channel,
  sku,
  category,
  TRY_CAST(qty          AS INT)    AS qty,
  TRY_CAST(unit_price   AS DOUBLE) AS unit_price,
  TRY_CAST(discount_pct AS DOUBLE) AS discount_pct,
  TRY_CAST(total_amount AS DOUBLE) AS total_amount,
  coupon_code
-- F: Lê incrementalmente os dados da tabela bronze que contém dados dos três volumes
FROM STREAM multi_flow_1_bronze.orders_bronze_flows_demo;

Revise o código - A: CREATE OR REFRESH STREAMING TABLE - Cria ou atualiza a tabela Silver multi_flow_2_silver.orders_silver_flows_demo e aplica um schema fixo para prevenir schema drift entre múltiplos flows.

  • B: CONSTRAINT ... EXPECT Aplica regras de qualidade de dados que descartam linhas com quantidades inválidas, totais negativos ou timestamps ausentes.

  • C: COMMENT Adiciona metadados descritivos explicando o propósito da tabela Silver.

  • D: CLUSTER BY AUTO Habilita liquid clustering automático, onde o Databricks escolhe de forma inteligente as clustering keys para otimizar a performance de suas queries. Você também pode especificar suas próprias clustering keys, se preferir.

  • E: TRY_CAST Garante tipos de coluna consistentes entre todas as subsidiárias, convertendo valores brutos em tipos de dados padronizados.

  • F: SELECT ... FROM STREAM Lê, seleciona e limpa incrementalmente os registros da bronze streaming table multi_flow_1_bronze.orders_bronze_flows_demo, que contém dados de três volumes separados.

F. Materialized Views de Business Intelligence

Materialized views no Lakeflow fornecem resultados pré-computados que potencializam analytics rápidos e confiáveis para usuários posteriores. Diferente de views comuns, elas atualizam automaticamente à medida que novos dados chegam, para que stakeholders sempre vejam insights atualizados sem exigir computação sob demanda.

NOTA: Esta seção assume familiaridade prévia com materialized views.

F1. Crie um Novo Arquivo SQL no seu Pipeline

  1. Clique no menu kebab ao lado da sua pasta ingest_multiple_flows e selecione Create file.
  2. Selecione a linguagem como SQL.
  3. Nomeie o arquivo como gold_mvs.sql.

F2. Crie Materialized Views Gold Simples

  1. Em seguida, você adicionará duas materialized views pequenas e simples para seus consumidores. Elas são usadas apenas para confirmar que seus dados silver estão limpos e prontos para análise. Materialized views não são o foco aqui, então vamos mantê-las simples.

a. A primeira materialized view fornece um resumo diário por subsidiária, permitindo verificar rapidamente receita, unidades e contagem de pedidos ao longo do tempo.

b. A segunda view destaca a performance básica de produtos, para que você veja quais categorias e SKUs estão vendendo dentro de cada subsidiária.

  1. Copie o código abaixo no seu arquivo gold_mvs.sql para criar ambas as materialized views.



------------------------------------------
-- a. MATERIALIZED VIEW GOLD: SCORECARD DIÁRIO POR SUBSIDIÁRIA
-- Resumo diário simples por subsidiária
------------------------------------------
CREATE OR REPLACE MATERIALIZED VIEW multi_flow_3_gold.mv_daily_subsidiary_scorecard_demo
AS
SELECT
  order_date,
  subsidiary_id,
  COUNT(DISTINCT order_id)    AS order_count,   -- quantos pedidos únicos ocorreram
  ROUND(SUM(total_amount),2)  AS total_revenue, -- receita total do dia
  SUM(qty)                    AS total_units    -- total de unidades vendidas
FROM multi_flow_2_silver.orders_silver_flows_demo
WHERE order_date IS NOT NULL
GROUP BY order_date, subsidiary_id;


------------------------------------------
-- b. MATERIALIZED VIEW GOLD: PERFORMANCE DE PRODUTO POR SUBSIDIÁRIA
-- Unidades e receita básicas por produto e subsidiária
------------------------------------------
CREATE OR REPLACE MATERIALIZED VIEW multi_flow_3_gold.mv_product_performance_by_subsidiary_demo
AS
SELECT
  subsidiary_id,
  category,
  sku,
  SUM(qty)                   AS units_sold,  -- total de unidades vendidas por SKU
  ROUND(SUM(total_amount),2) AS revenue      -- receita total por SKU
FROM multi_flow_2_silver.orders_silver_flows_demo
GROUP BY subsidiary_id, category, sku;

PYTHON
from pyspark.sql.functions import lit, sum as _sum
df_all = spark.sql(f"""
    SELECT 
        'bright_home_orders' AS Volume,
        COUNT(*) AS TotalRows,
        'bsh_orders_2025-11-02.csv' AS FileName
    FROM read_files('{my_vol_path}/bright_home_orders/bsh_orders_2025-11-02.csv')
    UNION ALL
    SELECT 
        'lumina_sports_orders' AS Volume,
        COUNT(*) AS TotalRows,
        'lms_orders_2025-11-02.csv' AS FileName
    FROM read_files('{my_vol_path}/lumina_sports_orders/lms_orders_2025-11-02.csv')
    UNION ALL
    SELECT 
        'northstar_outfitters_orders' AS Volume,
        COUNT(*) AS TotalRows,
        'nso_orders_2025-11-02.json' AS FileName
    FROM read_files('{my_vol_path}/northstar_outfitters_orders/nso_orders_2025-11-02.json')
""")
# Monta a linha TOTAL
total_row = (
    df_all
    .agg(_sum("TotalRows").alias("TotalRows"))
    .withColumn("Volume", lit("TOTAL"))
    .withColumn("FileName", lit(""))
    .select("Volume", "TotalRows", "FileName")  # mantém a ordem das colunas
)
# Anexa a linha TOTAL ao final
df_with_total = df_all.unionByName(total_row)
display(df_with_total)

H. Introdução à Adição de Tags em Objetos Bronze, Silver e Gold

Isso requer as permissões necessárias para adicionar tags

Nesta etapa você adiciona metadados semânticos às suas tabelas e materialized views. Tags facilitam a organização, busca e governança de objetos no Unity Catalog. Elas ajudam times posteriores a entender rapidamente o que cada objeto representa e como deve ser usado.

Você aplica dois tipos de tags:

  • Tags customizadas da demo
    Elas descrevem o departamento dono dos dados e o nível de qualidade na arquitetura medallion.
    Exemplos:
  • demo_tag_Department = 'Sales'

  • demo_tag_Quality = 'bronze' | 'silver' | 'gold'

  • Tags de sistema
    Estas são tags nativas do Unity Catalog. Aqui você adiciona a tag system.Certified para identificar objetos confiáveis e prontos para produção.

NOTA: Para mais informações, veja Apply tags to Unity Catalog securable objects
