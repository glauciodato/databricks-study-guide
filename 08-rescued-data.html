Aula - Trabalhando com a Coluna de Dados Resgatados

Visão Geral

Nesta aula, você aprenderá como a coluna de dados resgatados (_rescued_data) captura campos incompatíveis ou não analisáveis como JSON durante a ingestão de dados, preservando valores de Entrada não conformes nas suas tabelas do Lakehouse em vez de descartá-los.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de:

  1. Explicar o propósito da coluna de dados resgatados e como ela preserva dados não conformes durante a ingestão
  2. Descrever como as incompatibilidades de esquema são tratadas ao usar read_files(), spark.read ou Auto Loader
  3. Interpretar os valores de dados resgatados armazenados como strings JSON na coluna _rescued_data

EXPANDIR PARA NOTAS ADICIONAIS
Técnicas de ingestão como `read_files()`, `spark.read`, ou Auto Loader fornecem uma coluna de dados resgatados durante a ingestão: - A coluna de dados resgatados garante que colunas que não correspondem ao esquema sejam resgatadas em vez de descartadas - Valores incompatíveis são armazenados como strings no formato JSON na coluna _rescued_data - Se uma linha não apresentar incompatibilidades de esquema, a coluna _rescued_data será null - Isso preserva todos os dados de Entrada e evita a perda silenciosa de dados

Primeira linha: "Peter" e "$100"

_rescued_data é preenchido

Na primeira linha de dados, o valor "Peter" será lido corretamente na coluna users da tabela Bronze. No entanto, como a coluna cost contém uma string como $100, ela não corresponde ao tipo BIGINT esperado.

Como resultado, esse valor não será inserido na coluna cost. Em vez disso, será capturado na coluna _rescued_data, armazenado como uma string no formato JSON.
users cost _rescued_data
Peter null {"cost": "$100", "_file_path": "<file_path>"}

Segunda linha: "zebi" e 300

_rescued_data permanece vazio

Na segunda linha, ambos os valores são válidos: o valor "zebi" é uma STRING, e 300 é um BIGINT.

Portanto, essa linha será lida na tabela Bronze sem problemas, e a coluna _rescued_data permanecerá vazia para essa linha.
users cost _rescued_data
zebi 300 null
EXPANDIR PARA NOTAS ADICIONAIS
Por exemplo, suponha que seu local de armazenamento cloud contenha um conjunto de arquivos brutos (que podem ser CSV, TXT, JSON ou outros formatos) e que esses arquivos contenham uma coluna de usuários e uma coluna de custo. Ao ingerir esses dados, a coluna de usuários deve ser lida na tabela como STRING, e a coluna de custo deve ser lida como BIGINT. Na primeira linha de dados, o valor "Peter" será lido corretamente na coluna de usuários da tabela Bronze. No entanto, como a coluna de custo contém uma string como $100, ela não corresponde ao tipo BIGINT esperado. Como resultado, esse valor não será inserido na coluna de custo. Em vez disso, ele será capturado na coluna _rescued_data, armazenado como uma string no formato JSON. Na segunda linha, ambos os valores são válidos: o valor "zebi" é uma STRING e 300 é um BIGINT. Portanto, essa linha será lida na tabela Bronze sem problemas, e a coluna _rescued_data permanecerá vazia para essa linha.

C. Conclusão

Nesta aula, você aprendeu como a coluna de dados resgatados funciona durante a ingestão de dados:

  • Quando os dados de Entrada não correspondem ao esquema esperado, os valores incompatíveis são capturados na coluna _rescued_data como strings formatadas em JSON em vez de serem descartados.
  • A coluna de dados resgatados está disponível ao usar read_files(), spark.read ou Auto Loader.
  • Os valores que correspondem ao esquema são ingeridos normalmente, e _rescued_data é null para essas linhas.
  • Esse recurso evita a perda silenciosa de dados e permite inspecionar e tratar incompatibilidades de esquema após a ingestão.
