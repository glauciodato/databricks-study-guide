Protegendo Dados no Unity Catalog: Views e Controle de Acesso

Lição 1 de 5 · Views, Dynamic Views e o modelo de privilégios do Unity Catalog

A. Data Privacy como pilar de governança

Data Privacy no Databricks combina arquitetura Delta Lake, isolamento de dados e os recursos de governança do Unity Catalog para proteger dados sensíveis e manter conformidade com regulamentações como GDPR (Europa) e CCPA (Califórnia). Todo objeto protegido no Unity Catalog segue um namespace de três níveis: catalog.schema.object. Privilégios são avaliados de forma hierárquica ao longo dessa cadeia.

Por padrão, apenas o proprietário de um objeto (e admins do metastore) pode acessá-lo assim que criado — todo o resto precisa de privilégios explícitos ou herdados.

B. Views como camada de segurança por indireção

Uma view processa e expõe dados de uma tabela fonte sem exigir que o usuário tenha acesso direto à tabela. Isso acontece porque, ao consultar uma view, o Unity Catalog usa os privilégios do proprietário da view sobre a tabela fonte — não os privilégios de quem executa a query.

CREATE OR REPLACE VIEW customers_gold_view AS
SELECT
  customer_id,
  state,
  avg(units_purchased) as average_units_purchased,
  loyalty_segment
FROM customers_silver
GROUP BY customer_id, state, loyalty_segment;

Se outra pessoa tentasse consultar customers_silver diretamente (sem privilégios explícitos), a query falharia. Mas consultando a view, funciona — porque o proprietário da view tem acesso à tabela fonte por propriedade (ownership chaining).

C. Privilégios herdados vs. privilégios explícitos

O Unity Catalog suporta dois padrões para conceder acesso a dados. Use GRANT e REVOKE para gerenciá-los, e SHOW GRANTS ON securable_object para auditar.

AspectoPrivilégios HerdadosPrivilégios Explícitos
Setup1 GRANT no nível do Catálogo1 GRANT por schema/objeto
EscopoTodos objetos atuais e futuros no catálogoApenas os objetos especificados
RiscoAlto — fácil conceder acesso ao objeto erradoBaixo — acesso granular e intencional
Esforço operacionalBaixoAlto — escala mal com muitas tabelas/views
 
-- Herdado: acesso amplo, no nível do catálogo
GRANT USE CATALOG, USE SCHEMA, SELECT ON CATALOG my_catalog TO `account users`;

-- Explícito: acesso granular, objeto por objeto
GRANT USE SCHEMA ON SCHEMA my_catalog.pii_data TO `account users`;
GRANT SELECT ON VIEW my_catalog.pii_data.customers_gold_view TO `account users`;

-- Revogar acesso
REVOKE SELECT ON VIEW pii_data.customers_gold_view FROM `account users`;
Cuidado

Um GRANT no nível do catálogo se estende automaticamente a schemas e tabelas futuros. É conveniente para acesso em massa, mas aumenta o risco de expor dados que ainda serão criados.

D. Dynamic Views — controle de acesso condicional

Dynamic views são views padrão estendidas com funções que avaliam quem está executando a query, permitindo ocultar parcialmente colunas ou omitir linhas de forma condicional.

FunçãoRetorna
current_user()Email do usuário que consulta a view
is_account_group_member('group')TRUE se o usuário pertence ao grupo da conta especificado
is_member('group')TRUE se pertence ao grupo local do workspace (⚠️ desaconselhado em produção — cria dependência de workspace)
 
CREATE OR REPLACE VIEW customers_gold_dynamic_view AS
SELECT
  CASE WHEN                                  -- Redige customer_id se não for Supervisor
    is_account_group_member('supervisors') THEN customer_id
    ELSE 9999999
  END AS customer_id,
  state,
  avg(units_purchased) as average_units_purchased,
  loyalty_segment
FROM customers_silver
WHERE
  CASE WHEN                                  -- Oculta linhas de alta fidelidade se não for Supervisor
    is_account_group_member('supervisors') THEN TRUE
    ELSE loyalty_segment < 3
  END
GROUP BY customer_id, state, loyalty_segment;

Redações de coluna usam CASE WHEN no SELECT; filtragem de linhas usa a mesma lógica condicional em uma cláusula WHERE. Como proprietário, você não precisa de privilégios adicionais — mas ao consultar a própria view como um usuário comum, os dados aparecem ocultados exatamente como definido.

E. Conclusão

Views protegem tabelas por indireção via ownership chaining. Privilégios herdados (catalog-level) são convenientes mas arriscados; privilégios explícitos são seguros mas trabalhosos. Dynamic views usam is_account_group_member() com CASE WHEN para redigir colunas e filtrar linhas condicionalmente por usuário.

Key Takeaways
  • Namespace de três níveis: catalog.schema.object — privilégios avaliados hierarquicamente
  • Views dão acesso indireto via ownership chaining — proprietário da view precisa de acesso à tabela fonte, não o consumidor
  • Herdado (catalog-level) = conveniente, mas arriscado. Explícito (schema/objeto) = seguro, mas trabalhoso
  • Dynamic Views usam is_account_group_member() em CASE WHEN para redigir colunas e filtrar linhas por usuário

Row Filters, Column Masks e Governança de Dados

Lição 2 de 5 · UDFs de segurança, tagging, descobrimento e linhagem

A. Row Filters & Column Masks — a alternativa moderna às Dynamic Views

Introduzidos em 2024, Row Filters e Column Masks aplicam a mesma lógica condicional de segurança diretamente na tabela original — sem precisar criar um objeto adicional (a view). Os usuários continuam consultando a tabela pelo nome original.

AspectoDynamic ViewsRow Filters & Column Masks
Objeto extra?Sim — cria uma nova viewNão — aplicado direto na tabela
Nome referenciadoUsuários usam o nome da viewUsuários usam o nome original da tabela
ImplementaçãoCASE WHEN no SELECT/WHERE da viewUDF SQL + ALTER TABLE ... SET ROW FILTER / SET MASK
Quando usarAplicar transformação a tabelas somente leitura, nomes diferentes okPreservar o nome/tabela original para os usuários

B. Criando um Row Filter

Um filtro de linha é implementado como uma UDF SQL (ou UDF Python/Scala encapsulada em SQL) e aplicado à tabela com ALTER TABLE. Cada tabela pode ter apenas um filtro de linha, que aceita zero ou mais colunas como parâmetro.

1
Criar a UDF de filtro ▼
CREATE FUNCTION

A UDF usa is_account_group_member() para decidir se o usuário vê todas as linhas ou apenas um subconjunto.

CREATE OR REPLACE FUNCTION loyalty_row_filter(loyalty_segment STRING)
RETURNS BOOLEAN
RETURN IF(is_account_group_member('supervisors'), true, loyalty_segment < 3);
2
Aplicar o filtro à tabela ▼
ALTER TABLE ... SET ROW FILTER

A função é vinculada a uma coluna específica da tabela.

ALTER TABLE customers_silver_with_row_filter_and_column_masks
SET ROW FILTER loyalty_row_filter ON (loyalty_segment);
3
Criar a UDF de máscara ▼
CREATE FUNCTION

A máscara de coluna substitui o valor real por um valor mascarado, avaliada em tempo de execução da query.

CREATE OR REPLACE FUNCTION redact_customer_id(customer_id BIGINT)
RETURN CASE WHEN is_account_group_member('supervisors')
  THEN customer_id
  ELSE 9999999
END;
4
Aplicar a máscara à coluna ▼
ALTER TABLE ... SET MASK

A máscara é vinculada com ALTER COLUMN ... SET MASK.

ALTER TABLE customers_silver_with_row_filter_and_column_masks
  ALTER COLUMN customer_id
  SET MASK redact_customer_id;
5
Verificar via Information Schema ▼
INFORMATION_SCHEMA.ROW_FILTERS / COLUMN_MASKS

Confirme que o filtro/máscara foi aplicado consultando as tabelas de sistema.

SELECT * FROM information_schema.row_filters
WHERE table_name = 'customers_silver_with_row_filter_and_column_masks';

SELECT * FROM information_schema.column_masks
WHERE table_name = 'customers_silver_with_row_filter_and_column_masks';
Resultado

Consultando a tabela, um usuário fora do grupo supervisors vê customer_id = 9999999 em todas as linhas e apenas linhas com loyalty_segment < 3 — exatamente o mesmo resultado que a Dynamic View da lição anterior produzia, mas sem precisar de um objeto separado.

C. Tagging — organização e categorização

Tags são pares key-value opcionais aplicáveis a catálogos, schemas, tabelas, colunas, volumes, views, modelos e mais. Até 20 tags por objeto, key até 255 caracteres e valor até 1000 caracteres.

-- Tag na tabela
ALTER TABLE customers_silver
SET TAGS ('quality'='silver', 'domain'='customer');

-- Tag em uma coluna específica
ALTER TABLE customers_silver
  ALTER COLUMN customer_id SET TAGS ("compliance" = "GDPR");

Tags também podem ser gerenciadas pela interface do Catalog Explorer, sem código.

D. Descobrimento de Dados

Tags simplificam a descoberta de ativos de dados em toda a organização, de duas formas:

Search Bar
Sintaxe tag:value na barra de busca do workspace (ex: domain:customer). Quanto mais tags, mais refinados os resultados.
Queries via Information Schema
INFORMATION_SCHEMA.CATALOG_TAGS, SCHEMA_TAGS, TABLE_TAGS, COLUMN_TAGS, VOLUME_TAGS — recuperam tags programaticamente.

E. Linhagem e Documentação Gerada por IA

Linhagem (Lineage) é um pilar fundamental de qualquer solução de governança. No Catalog Explorer, a tab Lineage mostra Upstream (objetos que originaram este objeto — rastreia a fonte) e Downstream (objetos que consomem este objeto — útil para análise de impacto), além de um gráfico visual de relacionamentos.

Documentação Gerada por IA (DatabricksIQ) gera automaticamente descrições para tabelas, colunas, schemas e outros objetos com base no schema e nomenclatura — reduzindo esforço manual de documentação. Requer privilégio de proprietário ou MODIFY para editar/salvar.

F. Insights

A tab Insights no Catalog Explorer reporta, dos últimos 30 dias: queries e notebooks mais frequentes, dashboards mais usados, usuários frequentes e outras tabelas comumente unidas via join. Requer SELECT na tabela + USE SCHEMA/USE CATALOG nos objetos pai. Útil também para identificar tabelas não utilizadas, candidatas a limpeza.

G. Conclusão

Row Filters e Column Masks aplicam a mesma lógica de segurança condicional das Dynamic Views, mas direto na tabela original, sem objeto adicional. Tags organizam e viabilizam descoberta de dados. Linhagem rastreia fluxo upstream/downstream. Documentação por IA e Insights completam a governança do Unity Catalog.

Key Takeaways
  • Row Filter: UDF + ALTER TABLE ... SET ROW FILTER fn ON (coluna) — filtra linhas na tabela original
  • Column Mask: UDF + ALTER TABLE ... ALTER COLUMN ... SET MASK fn — mascara valores em tempo de query
  • Tags: até 20 por objeto, viabilizam busca (tag:value) e INFORMATION_SCHEMA.*_TAGS
  • Lineage: Upstream = origem dos dados. Downstream = análise de impacto

PII Data Security: Pseudonimização e Anonimização

Lição 3 de 5 · Hashing, tokenização e anonimização por binning com Spark Declarative Pipelines

A. Pseudonimização vs. Anonimização

São as duas principais estratégias de desidentificação para proteger dados de PII (Personally Identifiable Information). Ambas costumam ser combinadas em cenários reais.

AspectoPseudonimizaçãoAnonimização
ReversibilidadeReversível (com a chave/hash/tabela)Irreversível
EscopoNível de registro — ex: datasets para Machine LearningDataset inteiro (tabela/schema/catálogo) — ex: Business Intelligence
Status sob GDPRAinda é considerado dado pessoalDeixa de ser considerado dado pessoal
Técnicas principaisHashing, TokenizaçãoSupressão, Generalização (binning)

B. Pseudonimização — Hashing com Salt

Aplica SHA (ou outro hash) a todos os dados de PII, adicionando uma string aleatória ("salt") antes do hashing para dificultar ataques de dicionário. Databricks Secrets podem ofuscar o valor do salt em produção.

salt = "BEANS"

def salted_hash(id):
    return F.sha2(F.concat(id, F.lit(salt)), 256)

@dp.table
def user_lookup_hashed():
    return (dp.read_stream("registered_users")
            .select(
                salted_hash(F.col("user_id")).alias("alt_id"),
                "device_id", "mac_address"))
Nota

Teoricamente é possível reverter o pseudo-ID ao user_id original se a função de hash e o salt forem conhecidos — por isso um pseudônimo ainda é considerado dado pessoal pelo GDPR. A coluna original deve ser removida após o processamento em produção.

C. Pseudonimização — Tokenização

Converte o valor de PII em uma chave aleatória (token), armazenando o relacionamento original ↔ token em uma tabela de lookup segura e isolada.

@dp.table
def registered_users_tokens():
    return (dp.readStream("registered_users")
            .select("user_id")
            .distinct()
            .withColumn("token", F.expr("uuid()")))

@dp.table
def user_lookup_tokenized():
    return (dp.read_stream("registered_users")
            .join(dp.read("registered_users_tokens"), "user_id", "left")
            .drop("user_id")
            .withColumnRenamed("token", "alt_id"))
AspectoHashingTokenização
ArmazenamentoLeve aumento no tamanho dos dadosDados desidentificados em menos bytes
PerformanceAlgumas operações menos eficientesEscrita lenta, leitura rápida
DependênciaFunção + salt (não requer tabela extra)Requer tabela de lookup segura e isolada

D. Anonimização — Generalização por Binning

A generalização substitui um valor preciso (ex: idade exata) por uma faixa/categoria mais ampla, tornando reidentificação impossível. Diferente da pseudonimização, não há chave de reversão.

def age_bins(dob_col):
    age_col = F.floor(F.months_between(F.current_date(), dob_col) / 12).alias("age")
    return (
        F.when((age_col < 18), "under 18")
        .when((age_col >= 18) & (age_col < 25), "18-25")
        .when((age_col >= 25) & (age_col < 35), "25-35")
        # ... demais faixas
        .otherwise("invalid age")
        .alias("age")
    )

@dp.table
def user_age_bins():
    return (dp.read("users_bronze")
            .select("user_id", age_bins(F.col("dob")), "gender", "city", "state"))

O resultado: em vez de expor a data de nascimento exata, a tabela user_age_bins expõe apenas a faixa etária (ex: "25-35") — suficiente para analytics agregada, sem expor PII individual.

E. O pipeline completo com Spark Declarative Pipelines

Na prática, essas técnicas são orquestradas em um único Spark Declarative Pipeline com dois fluxos paralelos:

Fluxo de Pseudonimização
registered_users (Auto Loader) → user_lookup_hashed (salted hash) e registered_users_tokens + user_lookup_tokenized (tokenização)
Fluxo de Anonimização
user_events_raw (join com date_lookup) → users_bronze → user_age_bins (binning por idade)

O pipeline pode ser gerado e iniciado programaticamente via SDK (classe utilitária que abstrai chamadas REST API), com configuration centralizando os caminhos de origem — o mesmo padrão de parametrização visto no Capítulo 3.

F. Conclusão

Pseudonimização (hashing, tokenização) protege dados a nível de registro e é reversível — ainda é PII sob GDPR. Anonimização (binning) protege o dataset inteiro e é irreversível. Ambas são orquestradas como Spark Declarative Pipelines, reutilizando os conceitos de Streaming Tables e Materialized Views do Capítulo 3.

Key Takeaways
  • Pseudonimização = reversível, nível de registro, ainda é PII sob GDPR. Anonimização = irreversível, dataset inteiro
  • Hashing com salt: sha2(concat(id, salt), 256) — leve overhead, algumas operações menos eficientes
  • Tokenização: uuid() + tabela de lookup — escrita lenta, leitura rápida
  • Binning/Generalização: substitui valor exato por faixa (ex: idade → "25-35")

Change Data Feed: Propagando Alterações e Exclusões

Lição 4 de 5 · CDF, table_changes e direito ao esquecimento (GDPR/CCPA)

A. O que é Change Data Feed (CDF)

Change Data Feed rastreia alterações em nível de linha entre versões de uma tabela Delta. Quando habilitado, registra eventos de alteração para tudo que é escrito — incluindo metadados indicando se a linha foi inserida, atualizada ou excluída.

-- Habilitar globalmente para novas tabelas
spark.conf.set("spark.databricks.delta.properties.defaults.enableChangeDataFeed", True)

-- Habilitar em uma tabela existente
ALTER TABLE silver_users
SET TBLPROPERTIES (delta.enableChangeDataFeed = true);
Coluna de metadataTipoDescrição
_change_typeStringinsert, delete, update_preimage, update_postimage
_commit_versionLongVersão da tabela que contém a alteração
_commit_timestampTimestampMomento em que o commit foi criado

update_preimage = valor da linha antes da atualização. update_postimage = valor depois. Toda linha atualizada gera as duas entradas.

B. Lendo o CDF — duas abordagens

PySpark — readChangeData
cdf_df = (spark.read.format("delta")
    .option("readChangeData", True)
    .option("startingVersion", 2)
    .table("silver_users"))
SQL — table_changes()
SELECT * FROM table_changes("silver_users", 2)  -- (table, start [, end])
WHERE _change_type = "insert"

Ambas as opções aceitam startingVersion/startingTimestamp como ponto de partida na história da tabela, além de um fim opcional.

C. Upsert incremental com foreachBatch + MERGE INTO

Para transmitir alterações do bronze para o silver, uma função customizada usa foreachBatch para rodar um MERGE INTO a cada micro-lote — o padrão idêntico ao AUTO CDC INTO do Capítulo 3, mas escrito manualmente.

def upsert_to_delta(microBatchDF, batchId):
    microBatchDF.createOrReplaceTempView("updates")
    microBatchDF._jdf.sparkSession().sql("""
        MERGE INTO silver_users s
        USING updates u
        ON s.mrn = u.mrn
        WHEN MATCHED AND (s.dob <> u.dob OR s.city <> u.city /* ... */)
            THEN UPDATE SET *
        WHEN NOT MATCHED
            THEN INSERT *
    """)

(spark.readStream.table("bronze_users")
      .writeStream
      .foreachBatch(upsert_to_delta)
      .trigger(processingTime='3 seconds')
      .start())

D. Propagando exclusões — Direito ao Esquecimento (GDPR/CCPA)

Solicitações de exclusão ("direito ao esquecimento") costumam ter SLAs regulatórios e, por isso, são frequentemente processadas em um pipeline separado do ETL principal — rastreadas por uma tabela dedicada com prazo e status.

-- Tabela de acompanhamento com deadline e status
requests_df = (spark.readStream.table("user_delete_requests")
    .select("mrn", "request_date",
        F.date_add("request_date", 30).alias("deadline"),
        F.lit("requested").alias("status")))

-- Confirmar exclusão na tabela silver
DELETE FROM silver_users WHERE mrn IN (SELECT mrn FROM delete_requests);

-- Propagar via CDF para tabelas downstream (gold) + atualizar status
def process_deletes(microBatchDF, batchId):
    microBatchDF.createOrReplaceTempView("deletes")
    microBatchDF._jdf.sparkSession().sql("""
        MERGE INTO gold_users u USING deletes d
        ON u.mrn = d.mrn WHEN MATCHED THEN DELETE
    """)
    microBatchDF._jdf.sparkSession().sql("""
        MERGE INTO delete_requests dr USING deletes d
        ON d.mrn = dr.mrn WHEN MATCHED THEN UPDATE SET status = "deleted"
    """)

A chave natural (ex: mrn) rastreada pelo CDF permite propagar a mesma exclusão para múltiplas tabelas downstream em uma única operação incremental — vez de recomputar tudo.

Exclusão não é imediatamente total

Devido a como história de versões e CDF funcionam no Delta Lake, os valores excluídos continuam presentes em versões anteriores da tabela (SELECT ... VERSION AS OF 0 ainda os retorna). Para expurgar definitivamente arquivos de dados antigos, é necessário rodar VACUUM após o período de retenção do histórico.

E. Conclusão

CDF rastreia inserts/updates/deletes por versão via _change_type, _commit_version, _commit_timestamp. readChangeData (PySpark) e table_changes() (SQL) leem essas alterações. Exclusões de compliance (GDPR/CCPA) são melhor tratadas em pipeline separado, propagadas via CDF + MERGE, mas só são totalmente purgadas com VACUUM.

Key Takeaways
  • CDF: _change_type (insert/delete/update_preimage/update_postimage), _commit_version, _commit_timestamp
  • Leitura: option("readChangeData", True) (PySpark) ou table_changes(table, start[, end]) (SQL)
  • Exclusões de compliance (GDPR/CCPA) → tabela de tracking com deadline/status, processada separadamente do ETL principal
  • Deletes não são totais até rodar VACUUM — versões antigas ainda contêm os dados

Lab: Propagando Alterações com CDF

Lição 5 de 5 · Hands-on: habilitar CDF, ler mudanças e propagar deletes em múltiplas tabelas

A. Objetivo do laboratório

A tabela user_lookup vincula informações de identificação entre pipelines diferentes — é o ponto central a partir do qual mudanças devem ser propagadas. O laboratório usa CDF para excluir um usuário de user_lookup e propagar essa exclusão, via alt_id/user_id, para as tabelas downstream users e users_bin.

B. Passo a passo

1
Habilitar CDF na tabela user_lookup ▼
ALTER TABLE ... SET TBLPROPERTIES
ALTER TABLE user_lookup
SET TBLPROPERTIES (delta.enableChangeDataFeed = True);
2
Confirmar CDF habilitado ▼
DESCRIBE TABLE EXTENDED

Verifique a linha Table Properties nos resultados para confirmar delta.enableChangeDataFeed=true. Isso também gera a versão 1 na história da tabela.

DESCRIBE TABLE EXTENDED user_lookup;
DESCRIBE HISTORY user_lookup;  -- versão 1, operation = SET TBLPROPERTIES
3
Excluir um registro ▼
DECLARE VARIABLE + DELETE

Escolha um user_id e salve-o em uma variável de sessão para reutilizar nos próximos passos.

DECLARE OR REPLACE VARIABLE user_id INT DEFAULT 11745;

DELETE FROM user_lookup
WHERE user_id = session.user_id;
-- confirma: tabela cai de 100 para 99 linhas
-- DESCRIBE HISTORY user_lookup → versão 2, operation = DELETE
4
Ler o CDF gerado pela exclusão ▼
table_changes() / readChangeData

A partir da versão 1 (quando o CDF foi habilitado), apenas a linha excluída aparece como mudança.

-- SQL
SELECT * FROM table_changes("user_lookup", 1);

-- Python (opcional)
user_lookup_df = (spark.read.format("delta")
    .option("readChangeData", True)
    .option("startingVersion", 1)
    .table("user_lookup"))
display(user_lookup_df)
5
Isolar apenas as exclusões ▼
CREATE OR REPLACE TEMPORARY VIEW

Crie uma view temporária filtrando apenas linhas com _change_type = 'delete', a partir da versão 2 (a versão do DELETE).

CREATE OR REPLACE TEMPORARY VIEW user_lookup_deletes_vw AS
SELECT * FROM table_changes('user_lookup', 2)
WHERE _change_type = 'delete';
6
Propagar via MERGE INTO ▼
MERGE ... WHEN MATCHED THEN DELETE

Aplique a mesma exclusão nas duas tabelas downstream, usando as chaves correspondentes de cada uma.

MERGE INTO users u
USING user_lookup_deletes_vw ul
ON u.alt_id = ul.alt_id
WHEN MATCHED THEN DELETE;

MERGE INTO users_bin ub
USING user_lookup_deletes_vw ul
ON ub.user_id = ul.user_id
WHEN MATCHED THEN DELETE;
Resultado

Uma única exclusão em user_lookup se propaga, via CDF + MERGE INTO, para todas as tabelas downstream que compartilham a chave — sem reprocessar o dataset inteiro.

C. Validação

Cada operação de MERGE deve reportar num_affected_rows e num_deleted_rows iguais a 1. Uma query final filtrando o user_id excluído em users_bin deve retornar zero linhas, confirmando a propagação completa.

D. Conclusão

Este laboratório aplica de ponta a ponta o fluxo da lição anterior: habilitar CDF → identificar a mudança pela versão → isolar deletes com table_changes → propagar com MERGE INTO. O mesmo padrão se estende para qualquer número de tabelas downstream que compartilhem a chave de origem.

Key Takeaways
  • Habilitar CDF em uma tabela específica: ALTER TABLE ... SET TBLPROPERTIES (delta.enableChangeDataFeed = True)
  • table_changes(table, start) isola exatamente as linhas alteradas a partir de uma versão
  • Uma view temporária filtrando _change_type = 'delete' vira a fonte de um MERGE INTO ... WHEN MATCHED THEN DELETE
  • O mesmo padrão de propagação escala para N tabelas downstream compartilhando a mesma chave

Questão 1 de 8

Por que um usuário sem privilégios diretos na tabela fonte consegue consultar uma view criada sobre ela com sucesso?

✅ Esse comportamento é chamado ownership chaining: ao consultar uma view, o Unity Catalog verifica os privilégios do proprietário da view sobre os objetos que ela referencia — não os privilégios de quem executa a query.
Questão 2 de 8

Qual a principal desvantagem de conceder privilégios herdados no nível do catálogo (ex: GRANT SELECT ON CATALOG)?

✅ Um GRANT no nível do catálogo aplica-se a todos os schemas/tabelas atuais e futuros — muito conveniente, mas fácil de conceder acesso ao objeto errado sem perceber.
Questão 3 de 8

Qual função é usada em Dynamic Views e Row Filters/Column Masks para verificar se o usuário pertence a um grupo da conta?

✅ is_account_group_member('group') retorna TRUE/FALSE baseado em grupos da conta. is_member() existe mas é desaconselhado em produção por depender de grupos locais do workspace.
Questão 4 de 8

Qual a principal diferença entre Row Filters/Column Masks e Dynamic Views?

✅ Row Filters e Column Masks (2024+) aplicam a mesma lógica condicional das Dynamic Views, mas diretamente na tabela — os usuários continuam consultando pelo nome original, sem precisar de uma view intermediária.
Questão 5 de 8

Por que um pseudônimo (ex: gerado por hashing) ainda é considerado dado pessoal sob o GDPR, ao contrário de um dado anonimizado?

✅ Pseudonimização é reversível — quem conhece a chave/hash/salt pode reidentificar o titular. Por isso o GDPR ainda trata pseudônimos como dado pessoal. Anonimização é irreversível e não tem mais essa restrição.
Questão 6 de 8

Na anonimização por binning (ex: agrupar idade em faixas como "25-35"), qual técnica está sendo aplicada?

✅ Binning é uma forma de generalização: substitui um valor preciso (idade exata) por uma categoria mais ampla, uma das duas técnicas principais de anonimização (a outra é supressão).
Questão 7 de 8

Ao ler o Change Data Feed de uma tabela, o que representa uma linha com _change_type = "update_preimage"?

✅ update_preimage = valor antes da atualização. update_postimage = valor depois. Toda linha atualizada gera as duas entradas no CDF.
Questão 8 de 8

Uma empresa exclui um registro de um usuário via DELETE em compliance com uma solicitação de GDPR. Por que os dados ainda podem ser recuperados consultando uma versão anterior da tabela Delta (VERSION AS OF)?

✅ Delta Lake reescreve arquivos de dados em vez de apagá-los in-place, e mantém versões antigas para time travel. Para cumprir totalmente uma solicitação de exclusão, é necessário rodar VACUUM após o período de retenção configurado.
