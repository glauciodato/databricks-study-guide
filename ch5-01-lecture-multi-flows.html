Aula — Introdução a Multi Flows, Expectations e Liquid Clustering em SDP

Esta aula apresenta Flows em Spark Declarative Pipelines como o mecanismo principal para carregar e processar dados incrementalmente — incluindo como usar múltiplos flows para escrever em uma única target table. Em seguida, explora como Liquid Clustering e Data Quality Expectations são aplicados especificamente dentro do contexto de um pipeline declarativo.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de:

  • Explicar o que é um flow e como se relaciona com uma streaming table ou materialized view
  • Descrever a diferença entre um default flow e um explicit flow
  • Aplicar o padrão multi-flow para escrever de múltiplas fontes em uma única target table
  • Explicar por que multi-flow é preferível a UNION
  • Aplicar Data Quality Expectations a streaming tables em um Spark Declarative Pipeline
  • Aplicar Liquid Clustering a streaming tables para otimizar performance de queries em um Spark Declarative Pipeline

A. Entendendo Flows em Spark Declarative Pipelines

A1. O que é um Flow (Revisão...)

Flow = Query + Target

Query
SQL · Filters · Joins
→
FLOW
Unidade de Execução
←
Target
Streaming Table · MV
→
Resultado
Dados escritos no target

Um flow é a unidade básica de trabalho em um Spark Declarative Pipeline. Cada flow lê, processa e escreve dados independentemente, permitindo design de pipeline modular e escalável.

Query

A Query define de onde e como os dados são lidos — usando STREAM read_files(), FROM STREAM tabela, ou uma simples query SELECT — mais quaisquer transformações como filtros e joins.

Target

O Target define para onde os dados processados vão — uma streaming table ou materialized view. O target é declarado e gerenciado pelo pipeline.

Clique para Notas Adicionais

### Flow Um **flow** é a unidade básica de trabalho em um Spark Declarative Pipeline. Cada flow lê, processa e escreve dados independentemente, permitindo design de pipeline modular e escalável. ### Query (Fonte) A **query** é a parte de leitura e transformação do flow: - Ela define de onde os dados vêm (tabelas, arquivos, streams) - Quais transformações aplicar (filtros, joins, agregações) - Pode ser escrita em SQL ou Python - Determina o modo de processamento (incremental ou completo) ### Target (Destino) O **target** define onde os dados processados são escritos: - Pode ser uma **Streaming Table** ou **Materialized View** - O pipeline gerencia o ciclo de vida da tabela target automaticamente - O target possui estado: ele rastreia o que foi processado ### Conexão Flow Juntos, *query + target = flow*. O flow é a unidade de execução que orquestra uma leitura, transforma e escreve no destino.

A2. Ciclo de Vida do Flow e Gerenciamento de Checkpoint

Cada flow mantém seu próprio checkpoint — um marcador persistente que rastreia quais dados já foram processados. Isso permite que o pipeline retome exatamente de onde parou, processando apenas dados novos em cada execução.

Como um Flow processa dados:

  1. Primeira Execução — O flow processa todos os dados disponíveis e cria o checkpoint inicial
  2. Execuções Subsequentes — O flow lê o checkpoint, encontra dados novos desde a última execução e processa apenas os novos dados

Modos de Processamento

Modo Incremental (Padrão)

O modo incremental processa apenas novos dados desde o último checkpoint. Isso é altamente eficiente porque apenas dados novos precisam ser processados em cada execução.

  • Quando usar: Ingestão contínua de dados, processamento de novos registros, pipelines append-only

Modo Full Refresh

O modo Full Refresh reprocessa todos os dados do zero, descartando o checkpoint existente e reconstruindo a tabela completa. Isso é mais custoso e tipicamente reservado para casos onde todo o dataset precisa ser recalculado.

  • Quando usar: Após mudanças de schema, correção de dados, quando os dados precisam ser recalculados por completo

A3. Default Flow vs. Explicit Flow

Na maioria das vezes, um flow é criado automática e implicitamente quando você define uma streaming table ou materialized view. Este é o default flow — ele compartilha o mesmo nome do dataset target.

Quando você precisa de mais controle — como escrever de múltiplas fontes no mesmo target — você cria um explicit flow usando a cláusula CREATE FLOW. Explicit flows permitem nomear e gerenciar flows individuais de forma independente.

Default Flow — Criado implicitamente. Uma query, um target. Um flow por tabela.

-- Default flow: criado automaticamente
CREATE OR REFRESH STREAMING TABLE orders_bronze
AS SELECT * FROM STREAM read_files('path/to/orders')

Explicit Flow — Criado manualmente com CREATE FLOW. Múltiplas queries podem escrever no mesmo target.

-- Explicit flows: múltiplas fontes → um target
CREATE FLOW ingest_online
AS INSERT INTO orders_bronze BY NAME
SELECT * FROM STREAM read_files('path/to/online');

CREATE FLOW ingest_retail
AS INSERT INTO orders_bronze BY NAME
SELECT * FROM STREAM read_files('path/to/retail');

B. O Padrão Multi-Flow

B1. Escrevendo de Múltiplas Fontes em Um Único Target

O poder dos explicit flows é que você pode definir múltiplos flows apontando para a mesma tabela. Cada flow lê independentemente de uma fonte diferente e escreve na mesma streaming table. Isso é chamado de padrão multi-flow.

O target é definido uma vez como uma streaming table vazia (sem query), e cada flow é definido separadamente com sua própria query de ingestão.

-- 1. Defina a tabela target vazia
CREATE OR REFRESH STREAMING TABLE orders_bronze;

-- 2. Flow para pedidos online
CREATE FLOW online_orders
AS INSERT INTO orders_bronze BY NAME
SELECT * FROM STREAM read_files('/data/online_orders');

-- 3. Flow para pedidos da loja
CREATE FLOW retail_orders
AS INSERT INTO orders_bronze BY NAME
SELECT * FROM STREAM read_files('/data/retail_orders');

Cada flow mantém seu próprio checkpoint e processa dados independentemente. Isso proporciona melhor isolamento de erros — se um flow falhar, os outros continuam processando.

B2. Multi-Flow vs. UNION — Por que Importa

Uma alternativa comum ao multi-flow é combinar fontes com uma cláusula UNION dentro de uma única definição de streaming table. Para pipelines incrementais, isso é geralmente menos eficiente e mais frágil que o padrão multi-flow.

Aspecto Multi-Flow UNION
Checkpointing Cada flow rastreia seu progresso independentemente Um único checkpoint compartilhado entre todas as fontes
Isolamento de Falhas Se um flow falhar, os outros continuam Se uma fonte falhar, toda a ingestão para
Performance Cada flow processa apenas seus próprios dados novos Todas as fontes precisam ser escaneadas a cada execução
Evolução de Schema Cada flow pode evoluir de forma independente Mudanças de schema afetam toda a UNION
Observabilidade Métricas por flow (linhas, duração, erros) Métricas agregadas apenas

Resumo: Multi-flow é preferível porque oferece melhor isolamento, checkpoint independente e falha parcial em vez de falha total.

C. Data Quality Expectations

Data quality significa garantir que seu pipeline armazene apenas registros válidos e confiáveis. Em Spark Declarative Pipelines, você usa expectations para definir regras simples diretamente na definição da tabela. A cada execução do pipeline, cada linha é avaliada contra essas regras — e o resultado é registrado e aplicado automaticamente.

C1. Definindo Expectations em Streaming Tables

Em Spark Declarative Pipelines, constraints são definidas inline no bloco de definição de colunas da tabela usando CONSTRAINT ... EXPECT. Existem três modos de enforcement:

Modo Sintaxe Comportamento Quando Usar
WARN CONSTRAINT nome EXPECT (condição) Registra violações mas mantém a linha Monitoramento — não quer bloquear o pipeline
DROP CONSTRAINT nome EXPECT (condição) ON VIOLATION DROP ROW Remove linhas inválidas silenciosamente Dados ruins devem ser excluídos
FAIL CONSTRAINT nome EXPECT (condição) ON VIOLATION FAIL UPDATE Para o flow com erro Dados críticos devem estar corretos

As expectations são avaliadas por linha durante a escrita. As métricas (quantas passaram/falharam) são automaticamente rastreadas e visíveis na UI do Pipeline e nas system tables.

C2. Exemplo de Implementação de Expectations

Aqui está um exemplo abrangente mostrando como implementar expectations de data quality em uma streaming table:

CREATE OR REFRESH STREAMING TABLE orders_silver
(
  -- WARN: registra se order_id está nulo, mas mantém a linha
  CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL),

  -- DROP: remove linhas com valor total inválido
  CONSTRAINT valid_total EXPECT (total > 0) ON VIOLATION DROP ROW,

  -- FAIL: para o flow se houver tipo de pedido desconhecido
  CONSTRAINT valid_type EXPECT (order_type IN ('online', 'retail', 'wholesale'))
    ON VIOLATION FAIL UPDATE
)
AS SELECT
  order_id,
  customer_id,
  order_type,
  total,
  order_date
FROM STREAM orders_bronze

Neste exemplo: - valid_order_id — registra um aviso se order_id for nulo, mas a linha continua no target - valid_total — remove silenciosamente linhas onde total não é positivo - valid_type — para o flow se encontrar um order_type que não é 'online', 'retail' ou 'wholesale'

C3. Monitoramento e Observabilidade

Expectations de data quality geram automaticamente métricas acessíveis por dois canais:

  • UI do Pipeline para saúde visual rápida
  • System tables para análise profunda com SQL

Métricas na UI do Pipeline

Na aba de detalhes do dataset, métricas de flow mostram contagens de registros e taxas de pass/fail de expectations para cada execução, permitindo que você identifique rapidamente problemas de data quality.

System Tables para Análise Profunda

Use system tables para consultar métricas de expectations com SQL, permitindo rastreamento histórico de tendências e alertas automatizados.

-- Consultar resultados de expectations via system table
SELECT
  dataset_name,
  expectation_name,
  passed_records,
  failed_records,
  ROUND(failed_records * 100.0 / (passed_records + failed_records), 2) AS pct_failed
FROM system.lakeflow.flow_progress_expectations
WHERE pipeline_id = '<seu-pipeline-id>'
ORDER BY timestamp DESC

D. Liquid Clustering em Spark Declarative Pipelines

D1. O que é Liquid Clustering?

Liquid Clustering é uma técnica de otimização de layout de dados no Delta Lake que substitui o particionamento Hive-style tradicional e Z-Ordering. Ele organiza arquivos de dados baseado em colunas de clustering que você especifica, otimizando a performance de queries agrupando dados relacionados.

Benefícios do Liquid Clustering:

Benefício Descrição
Automático Otimiza dados automaticamente — sem necessidade de OPTIMIZE ou ZORDER manual
Adaptativo Adapta-se a mudanças de padrões de query ao longo do tempo
Incremental Só reorganiza dados novos ou modificados — não o dataset inteiro
Simples Uma cláusula CLUSTER BY substitui particionamento + Z-ordering

Quando Usar Liquid Clustering:

  • Tabelas frequentemente filtradas por colunas específicas (data, região, tipo)
  • Tabelas com volumes de dados crescentes onde performance de queries importa
  • Como substituto de particionamento Hive-style e Z-ordering combinados

D2. Como Liquid Clustering Funciona

Abaixo está uma série de snapshots ilustrando como liquid clustering funciona. Temos uma tabela de vendas onde as colunas de clustering são definidas como Date e Customer Id (representadas por cores).

Sem Clustering

Dados são escritos conforme chegam — nenhuma organização. Queries que filtram por data ou cliente precisam escanear todos os arquivos.

Com Liquid Clustering

Dados são reorganizados com base nas colunas de clustering. Queries que filtram por essas colunas pulam arquivos irrelevantes — data skipping significativo.

Após Novos Dados

Quando novos dados chegam, apenas os novos arquivos são reorganizados incrementalmente. Dados existentes não precisam ser re-clusterizados (ao contrário de Z-ordering que reprocessa tudo).

D3. Aplicando Liquid Clustering a Streaming Tables em SDP

Você já está familiarizado com Liquid Clustering em Delta tables. Em Spark Declarative Pipelines, ele é habilitado diretamente na definição da streaming table com a cláusula CLUSTER BY.

-- Liquid Clustering em uma streaming table
CREATE OR REFRESH STREAMING TABLE orders_silver
CLUSTER BY (order_date, region)
AS SELECT *
FROM STREAM orders_bronze

Pontos-Chave:

  • CLUSTER BY é aplicado na definição da tabela — não como operação separada
  • O clustering acontece automaticamente durante atualizações do pipeline
  • Não há necessidade de executar OPTIMIZE ou ZORDER manualmente
  • As colunas de clustering podem ser alteradas a qualquer momento sem recriar a tabela

CLUSTER BY AUTO

Use CLUSTER BY AUTO para deixar o Databricks selecionar automaticamente as melhores colunas de clustering baseado nos padrões de query reais.

-- Deixe o Databricks escolher as colunas de clustering automaticamente
CREATE OR REFRESH STREAMING TABLE orders_silver
CLUSTER BY AUTO
AS SELECT * FROM STREAM orders_bronze

D4. Seleção de Estratégia de Clustering

Estratégia Colunas Quando Usar
CLUSTER BY (colunas) Você especifica as colunas Quando você conhece os padrões de query e quer controle total
CLUSTER BY AUTO Databricks seleciona automaticamente Melhor para tabelas novas ou quando você não conhece os padrões de query ainda

CLUSTER BY AUTO é melhor para: - Tabelas novas onde padrões de query ainda não são conhecidos - Quando você quer que o Databricks escolha automaticamente o melhor clustering - Quando padrões de query mudam com o tempo

CLUSTER BY (colunas) é melhor para: - Quando você conhece exatamente os filtros mais comuns das queries - Quando quer controle total sobre a estratégia de clustering - Tabelas maduras com padrões de acesso bem definidos

CLIQUE PARA NOTAS ADICIONAIS

#### Quando usar CLUSTER BY AUTO - Melhor para tabelas novas ou quando você não conhece seus padrões de query ainda - Deixa o Databricks escolher automaticamente o melhor clustering baseado em queries reais - Adapta-se ao longo do tempo conforme os padrões de query mudam #### Quando usar CLUSTER BY (colunas) - Quando você sabe exatamente quais colunas são filtradas com mais frequência - Dá controle total sobre a estratégia de clustering - Melhor para tabelas estabelecidas com padrões de acesso previsíveis

CLICK FOR ADDITIONAL NOTES

#### When to use CLUSTER BY AUTO - Best for new tables or when you don't know your query patterns yet - Lets Databricks automatically pick the best clustering keys based on actual queries - Adapts as your table grows or query patterns change - No manual tuning required — Databricks keeps optimizing in the background #### When to use CLUSTER BY (columns) - Use when you know exactly which columns are most often filtered in your queries - Gives you full control and predictable clustering layout - Ideal for stable workloads with consistent filter columns - Recommended for regulatory or performance-critical tables #### How AUTO Actually Works Databricks does not blindly pick columns — it runs a continuous **cost-benefit analysis** behind the scenes. Clustering keys are only changed when the predicted savings from data skipping outweigh the cost of reorganizing data files.
