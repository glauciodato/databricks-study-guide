Aula — Verificações Avançadas de Data Quality e Expectations em Spark Declarative Pipelines

Em data pipelines de produção, data quality é primordial. Enquanto Spark Declarative Pipelines fornecem expectations built-in para validação básica, ambientes de produção exigem abordagens mais sofisticadas. Esta aula explora técnicas avançadas para construir pipelines resilientes que mantêm data quality sem perder dados.

Objetivos de Aprendizado

Ao final desta aula, você será capaz de: - Escrever expectations avançadas para validação cross-table e tolerantes a NULL - Projetar ingestão resiliente usando STRING types e schema evolution - Implementar o padrão Quarantine para zero perda de dados

A. Por que Expectations Avançadas?

A1. Os Limites das Expectations Básicas

Uma verificação NOT NULL confirma que um campo está presente — mas presença sozinha não significa que o valor é correto. A tabela abaixo mostra como expectations básicas perdem problemas comuns de data quality:

Verificação Básica O que Captura O que Não Captura
IS NOT NULL Campos ausentes Valores inválidos (ex: "abc" em campo numérico)
> 0 Zeros e negativos Valores fora de range razoável (ex: idade = 999)
IN ('A','B') Valores fora da lista Valores válidos mas incorretos para o contexto

Expectations Avançadas cobrem:

  • Validação de range: valores devem estar dentro de limites razoáveis
  • Validação cross-table: valores devem existir em tabela de referência
  • Validação temporal: datas devem estar em ranges válidos
  • Constraints compostas: múltiplas condições combinadas

A2. Padrões Avançados de Expectations

Além de constraints por linha, Databricks expectations suportam validação cross-table. Esses padrões permitem verificar contagens de linhas, detectar registros ausentes e validar integridade referencial.

-- Validação cross-table: verificar que silver tem todas as linhas do bronze
CONSTRAINT row_count_match
  EXPECT (silver_count = bronze_count)
  ON VIOLATION FAIL UPDATE

-- Validação de range com tolerância a NULL
CONSTRAINT valid_age
  EXPECT (age IS NULL OR (age >= 0 AND age <= 150))

-- Constraint composta
CONSTRAINT valid_order
  EXPECT (quantity > 0 AND unit_price > 0 AND total = quantity * unit_price)
  ON VIOLATION DROP ROW

A3. Escrevendo Constraints Tolerantes a NULL

Cada bloco CONSTRAINT deve validar uma única regra lógica. Isso dá à UI do pipeline métricas precisas por constraint. Mas quando uma coluna pode ser NULL, a constraint precisa lidar com isso explicitamente.

-- ❌ ERRADO: falha para NULLs (NULL > 0 = NULL = falha)
CONSTRAINT valid_total EXPECT (total > 0)

-- ✅ CORRETO: tolerante a NULL
CONSTRAINT valid_total EXPECT (total IS NULL OR total > 0)

Por que isso importa: Em SQL, qualquer comparação com NULL retorna NULL (não TRUE nem FALSE). Uma constraint que espera total > 0 vai falhar para linhas onde total é NULL — mesmo que NULL seja um valor aceitável que será tratado downstream.

A regra é: se NULL é aceitável para um campo, inclua IS NULL OR na constraint.

Regra de Ouro para Constraints Sempre considere NULLs ao escrever constraints. Se NULL é aceitável, use o padrão IS NULL OR (condição). Se NULL NÃO é aceitável, adicione uma constraint separada IS NOT NULL.

B. Design de Pipeline Resiliente

B1. Ingerir Tudo como STRING

O design de bronze layer mais resiliente nunca rejeita um registro por incompatibilidade de tipo. Ao armazenar todos os campos como STRING, você aceita todos os registros, e conversões de tipo acontecem na camada silver onde dados inválidos podem ser tratados adequadamente.

-- Bronze: ingerir tudo como STRING
CREATE OR REFRESH STREAMING TABLE raw_events
AS SELECT
  CAST(value AS STRING) AS raw_value,
  _metadata.file_name AS source_file,
  current_timestamp() AS ingestion_time
FROM STREAM read_files('/data/events', format => 'JSON')

Benefícios: Zero perda de dados na ingestão. Schema mismatches são capturados como strings. Validação e casting acontecem na silver layer onde problemas podem ser tratados.

B2. Ferramentas de Schema Evolution na Bronze Layer

Dois mecanismos built-in cobrem o ciclo de vida completo de mudanças de schema:

Ferramenta O que Faz Quando Usar
schemaEvolutionMode = 'addNewColumns' Adiciona automaticamente novas colunas dos dados fonte Quando fontes adicionam campos novos ao longo do tempo
Rescued Data Column Captura campos que não encaixam no schema atual como JSON Como fallback para mudanças de schema inesperadas 
-- Schema evolution + rescued data
CREATE OR REFRESH STREAMING TABLE bronze_events
AS SELECT *, _rescued_data
FROM STREAM read_files(
  '/data/events',
  format => 'JSON',
  schemaEvolutionMode => 'addNewColumns'
)

C. O Padrão Quarantine

C1. Como o Padrão Quarantine Funciona

O padrão quarantine roteia cada registro de entrada pela avaliação de qualidade, e então divide a saída em dois caminhos baseados nos resultados — caminho limpo para analytics e caminho quarantine para investigação.

Fluxo: 1. Bronze table recebe todos os dados raw 2. Silver Clean: recebe apenas registros que passam em TODAS as expectations 3. Silver Quarantine: recebe registros que falharam em qualquer expectation

Nenhum dado é perdido — registros inválidos são isolados para investigação e possível recuperação, em vez de serem descartados permanentemente.

C2. Zero Perda de Dados com Lógica Inversa

DROP ROW deleta permanentemente registros inválidos — sem caminho de recuperação. O padrão quarantine elimina perda de dados completamente usando lógica inversa:

-- Tabela CLEAN: mantém registros que passam em TODAS as validações
CREATE OR REFRESH STREAMING TABLE silver_clean
(
  CONSTRAINT valid_email EXPECT (email IS NOT NULL AND email LIKE '%@%')
    ON VIOLATION DROP ROW,
  CONSTRAINT valid_amount EXPECT (amount > 0)
    ON VIOLATION DROP ROW
)
AS SELECT * FROM STREAM bronze_events;

-- Tabela QUARANTINE: captura registros que falharam (lógica INVERSA)
CREATE OR REFRESH STREAMING TABLE silver_quarantine
AS SELECT * FROM STREAM bronze_events
WHERE NOT (
  (email IS NOT NULL AND email LIKE '%@%')
  AND (amount > 0)
);

O truque: A tabela quarantine usa a condição inversa (NOT) das expectations. Registros que seriam dropados pela clean table são capturados pela quarantine table.

C3. Escolhendo Entre DROP ROW e Quarantine

Ambas as estratégias enforçam data quality, mas diferem fundamentalmente no que acontece com registros inválidos. A escolha correta depende se seu negócio pode tolerar perda de dados.

Aspecto DROP ROW Quarantine
Dados inválidos Deletados permanentemente Isolados para investigação
Recuperação Impossível Possível após correção
Complexidade Simples (uma tabela) Maior (duas tabelas + lógica inversa)
Perda de dados Sim Não
Melhor para Dados ruidosos de baixo valor Dados de alto valor que não podem ser perdidos
Auditoria Apenas métricas de contagem Registros completos preservados

Recomendação: Use Quarantine quando dados são valiosos ou regulamentados. Use DROP ROW quando dados inválidos são ruído de baixo valor que não vale a pena preservar.

C3. Choosing Between DROP ROW and Quarantine

Both strategies enforce data quality, but they differ fundamentally in what happens to invalid records. The right choice depends on whether your business needs an audit trail, recovery capability, and whether false violations from schema evolution are a concern.

DROP ROW Quarantine Pattern
Invalid records Permanently deleted Preserved in quarantine table
Audit trail None Full — queryable
Data recovery Not possible Fix rule → re-route from quarantine
UI violation metrics Visible in pipeline UI Per-constraint metrics via WARN
Read performance Full table scan on clean data Partition pruning on is_quarantined
Pipeline complexity Low — single table Moderate — temp table + 2 views
Best for Non-critical streams with well-established rules Production pipelines with compliance, audit, or remediation needs
Recommendation: For enterprise production pipelines, the quarantine pattern is the preferred approach. It gives you zero data loss, per-constraint violation metrics in the pipeline UI, partition-pruned reads on clean data, and a recoverable quarantine table for root cause analysis and reprocessing — capabilities that DROP ROW cannot provide.
